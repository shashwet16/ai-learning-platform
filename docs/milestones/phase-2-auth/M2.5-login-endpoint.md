# M2.5 — Login Endpoint

## One-line summary
`POST /auth/login` exchanges valid credentials for a JWT — and does it in a way that resists timing-based email enumeration.

## The problem
Given an email and password, verify them against the stored hash and issue an access token — but do it without accidentally leaking *which* emails are registered to an attacker probing the endpoint.

## What we built
```python
_DUMMY_HASH = hash_password("dummy-password-for-constant-time-login")

@router.post("/login", response_model=Token)
def login(body: UserLogin, db: Session = Depends(get_db)) -> Token:
    user = db.execute(select(User).where(User.email == body.email)).scalar_one_or_none()

    hashed_password = user.hashed_password if user is not None else _DUMMY_HASH
    password_is_valid = verify_password(body.password, hashed_password)

    if user is None or not password_is_valid:
        raise AppError("Incorrect email or password", status_code=401, code="invalid_credentials")

    access_token = create_access_token(str(user.id))
    return Token(access_token=access_token)
```

## How it works — the timing attack this specifically defends against
bcrypt verification (M2.2) is deliberately slow — that's the whole point for resisting brute force. But that slowness creates a *side channel* if it's only run conditionally: if the code looked like `if user is None: return 401 immediately`, that early return is fast (just a database lookup, no bcrypt), while a *wrong password for a real account* takes measurably longer (a full bcrypt verify runs). An attacker who can measure response time — trivially scriptable — can tell "no such account" (fast response) apart from "account exists, wrong password" (slow response) without ever seeing an error message that admits it, and use that to enumerate every registered email address one probe at a time.

The fix: `verify_password` runs on *every* login attempt, unconditionally — against the real hash if the user exists, or against `_DUMMY_HASH` (a hash of an arbitrary fixed string, precomputed once at import time) if they don't. Both paths now do the same amount of expensive work, so response time no longer reveals whether the email exists. Only *after* that constant-time-shaped check does the code branch on `user is None or not password_is_valid` — and both failure reasons return the exact same error message and code (`invalid_credentials`), never "wrong password" vs. "no such user," so there's no information leak in the response content either.

## Why this matters enough to engineer around
Email enumeration seems minor in isolation, but it's a real building block for larger attacks: confirming which emails have accounts on a platform is reconnaissance for targeted phishing, credential-stuffing prioritization (only try leaked passwords against emails confirmed to exist here), and privacy violations (e.g. confirming someone has an account on a sensitive platform). It's a well-known category (OWASP calls it out explicitly) worth defending against even in a learning-platform context, both because it's genuinely good practice and because it's a strong interview signal — most naive login implementations get this wrong.

## Terms worth knowing
- **Timing attack**: inferring secret information (here: whether an email is registered) from how *long* an operation takes, rather than from its explicit output.
- **Side channel**: any unintended information leak through a system's observable behavior (timing, error messages, response size) rather than its documented interface.
- **Email/username enumeration**: confirming which identifiers have valid accounts on a system, typically a precursor to more targeted attacks.

## If asked in an interview
> "Login always runs a full bcrypt verify, even when the email doesn't exist — against a precomputed dummy hash in that case — so a nonexistent email and a wrong password take the same amount of time and return the identical error. Without that, the bcrypt verify's deliberate slowness becomes a timing side channel: 'no such account' returns fast, 'wrong password' returns slow, and an attacker can enumerate registered emails just by measuring response time, without either error message ever admitting the difference."
