# M2.9 — Protected Route Wrapper

## One-line summary
`ProtectedRoute` gates every authenticated-only page in one place, redirecting to `/login` if you're not signed in — and correctly waits during the initial "are we actually logged in?" check.

## The problem
Pages like `/courses`, `/chat`, and the dashboard should never render for a logged-out visitor. Checking `if (!user) redirect` inside every single page component would be repetitive and easy to forget on a newly added page.

## What we built
`frontend/src/components/ProtectedRoute.tsx`:
```typescript
export function ProtectedRoute() {
  const { user, isLoading } = useAuth()

  if (isLoading) {
    return <p className="loading-screen">Loading…</p>
  }
  if (!user) {
    return <Navigate to="/login" replace />
  }
  return <Outlet />
}
```
Wired into `App.tsx`'s route tree so every page nested under it inherits the guard:
```tsx
<Route element={<ProtectedRoute />}>
  <Route element={<AppLayout />}>
    <Route path="/" element={<HomePage />} />
    <Route path="/courses" element={<CoursesPage />} />
    ...
  </Route>
</Route>
```

## How it works
`react-router-dom`'s `<Outlet />` renders whichever *child* route actually matched — `ProtectedRoute` itself renders no page content at all, it's purely a gate: render the real page (`<Outlet />`) if authorized, or redirect if not. This "layout route" pattern lets an entire subtree of routes share one guard by nesting under it, rather than each page individually importing and calling a guard function.

The `isLoading` check is the subtle, easy-to-get-wrong part, and the code comments on it directly:
```typescript
// Don't decide anything while the mount-time /auth/me check (see M2.7)
// is still in flight — on a fresh page load with a valid stored token,
// `user` starts out null for a moment before that check resolves.
```
Recall from M2.7: on a fresh page load, `AuthContext` starts with `user = null` and only populates it *after* an async `/auth/me` call resolves. Without the `isLoading` check, `ProtectedRoute` would see `user === null` during that brief window and redirect to `/login` — incorrectly bouncing an already-logged-in user (with a perfectly valid stored token) to the login page, purely because the verification request hadn't finished yet. `isLoading` distinguishes "we don't know yet" from "we checked, and there's no user" — three states, not two, correctly modeled.

`<Navigate to="/login" replace />` — the `replace` flag matters: it swaps the current browser history entry instead of pushing a new one, so clicking "back" after being redirected doesn't return to the protected page that just bounced you (which would immediately bounce you again) — it goes to whatever was open before that.

## Why a wrapper route component (not a check inside every page)
- **Impossible to forget**: adding a new authenticated page means nesting it under the existing `<Route element={<ProtectedRoute />}>` in `App.tsx` — the guard is structural, not something to remember to add per-page.
- **One place to get the loading-state subtlety right**: that three-state (`loading` / `no user` / `user`) logic only needs to be correct once, not re-derived (and potentially re-broken) in every page component.

## Terms worth knowing
- **Layout route / wrapper route**: a route in `react-router-dom` that renders shared structure (or, here, a guard) around its nested child routes via `<Outlet />`, rather than rendering page content of its own.
- **Race condition (UI version)**: here, the risk of a decision (redirect or not) being made based on state that hasn't finished loading yet — resolved by explicitly tracking a loading flag rather than assuming any particular ordering of async operations.

## If asked in an interview
> "`ProtectedRoute` is a layout route wrapping every authenticated page via `<Outlet />`, so the guard exists in exactly one place instead of being repeated per page. The detail that actually took some care: it has to distinguish 'still checking whether you're logged in' from 'confirmed logged out' — without that, a page refresh with a perfectly valid stored token would flash-redirect to `/login` during the brief window before the `/auth/me` verification call resolves, since `user` starts as `null` either way until that check completes."
