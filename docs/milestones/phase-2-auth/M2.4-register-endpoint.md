# M2.4 — Register Endpoint

## One-line summary
`POST /auth/register` — new users can sign up, with duplicate emails rejected and the password hash never echoed back.

## The problem
The first real user-facing auth flow: turn an email/password/name into a persisted `User` row, safely.

## What we built
`backend/app/schemas/user.py` (`UserCreate`, `UserRead`) and `backend/app/api/routes/auth.py`'s `register()`:
```python
@router.post("/register", response_model=UserRead, status_code=201)
def register(body: UserCreate, db: Session = Depends(get_db)) -> User:
    user = User(email=body.email, hashed_password=hash_password(body.password),
                full_name=body.full_name)
    db.add(user)
    try:
        db.commit()
    except IntegrityError as exc:
        db.rollback()
        raise AppError("Email already registered", status_code=409, code="email_taken") from exc
    db.refresh(user)
    return user
```

## How it works
- **`UserCreate` vs. `UserRead` — two different Pydantic schemas for the same resource.** `UserCreate` is the *input* shape (`email`, `password` with `Field(min_length=8)`, `full_name`); `UserRead` is the *output* shape (`id`, `email`, `full_name`, `created_at` — no password field at all). `response_model=UserRead` means FastAPI filters the returned `User` ORM object down to only those fields before serializing — even if a route accidentally returned the whole object including `hashed_password`, the response model guarantees it's never exposed to the client. This input/output schema split is the pattern every other resource in the project follows (`ExerciseRead` vs. `ExerciseSubmissionCreate`, `CourseSummary` vs. `CourseDetail`, etc.).
- **Catching `IntegrityError`, not pre-checking "does this email exist"**: as noted in M2.1, a pre-check-then-insert has a race condition — two requests could both pass the check before either commits. Letting the database's own unique constraint be the actual enforcement point, and catching the resulting `IntegrityError` to turn it into a clean `409 email_taken`, closes that race entirely — the database serializes the two commits and only one can win.
- **`db.rollback()` before raising** — necessary because a failed commit leaves the session in a state where it can't be reused without explicitly rolling back first; skipping this would leave the session broken for any code that runs afterward (e.g. this same request's exception handler, or connection-pool reuse for the next request on that connection).

## Why register alone doesn't return a token
Looking ahead: `register()` returns a `UserRead`, not a `Token` — logging in still requires a separate `POST /auth/login` call afterward (see M2.5, and M2.8's frontend page, which calls `register()` then immediately `login()` with the same credentials so the user experience is still "one click to a logged-in session"). Keeping register and login as separate, single-purpose endpoints is simpler to reason about and test independently, at the cost of one extra round trip the frontend has to make on the caller's behalf.

## Terms worth knowing
- **Request schema vs. response schema**: the shape of data a client sends in vs. the shape a client receives back — deliberately different when the two shapes need different fields (a password is write-only; a database ID doesn't exist until after creation).
- **`response_model`**: FastAPI's mechanism for declaring the output shape explicitly and filtering/validating the returned object against it — a safety net against accidentally leaking fields.
- **Idempotency vs. this endpoint**: registering twice with the same email is *not* idempotent — it fails the second time (409), which is the correct behavior for "create a new thing," as opposed to an endpoint like `PUT /users/{id}` which typically is idempotent.

## If asked in an interview
> "Register uses separate input (`UserCreate`) and output (`UserRead`) schemas — the output schema has no password field at all, so there's no way for the endpoint to accidentally leak the hash even by mistake. Duplicate-email handling relies on the database's own unique constraint and catching `IntegrityError`, not a pre-check query, which avoids a race condition where two simultaneous signups with the same email could both pass a naive existence check."
