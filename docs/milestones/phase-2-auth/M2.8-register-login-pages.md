# M2.8 — Register & Login Pages

## One-line summary
The actual forms a person types into — wired to `AuthContext`, with inline validation errors and no dead-ends.

## The problem
`AuthContext` (M2.7) provides `login()`/`register()` as functions, but nobody can sign up or log in until there's a UI to call them from.

## What we built
`frontend/src/pages/LoginPage.tsx` and `frontend/src/pages/RegisterPage.tsx` — controlled forms using React's `useState` for each field, calling into `useAuth()`.

## How it works
Both forms follow the same shape:
```typescript
const [email, setEmail] = useState('')
const [error, setError] = useState<string | null>(null)
const [isSubmitting, setIsSubmitting] = useState(false)

async function handleSubmit(event: FormEvent) {
  event.preventDefault()
  setError(null)
  setIsSubmitting(true)
  try {
    await login(email, password)
    navigate('/')
  } catch (err) {
    setError(err instanceof ApiError ? err.message : 'Something went wrong. Please try again.')
  } finally {
    setIsSubmitting(false)
  }
}
```
- **Controlled inputs**: every `<input>`'s `value` is driven by React state (`value={email}`, `onChange={(e) => setEmail(e.target.value)}`) rather than letting the DOM own the input's value — this is the standard React form pattern, needed so the component's state is always the single source of truth (e.g. for the password's `minLength={8}` to be meaningfully checked against the same value that gets submitted).
- **`event.preventDefault()`**: stops the browser's native form submission (which would trigger a full page reload/navigation) so the submit is instead handled entirely by this async function.
- **`isSubmitting` disables the button and swaps its label** (`'Logging in…'`) — prevents a double-submit from an impatient double-click, and gives immediate feedback that something is happening during the network round trip.
- **Typed error narrowing**: `err instanceof ApiError ? err.message : 'Something went wrong...'` — if the thrown error is the app's own typed `ApiError` (M2.7), its `.message` is the backend's actual error text (e.g. "Incorrect email or password"); any other kind of thrown error (a network failure, a bug) falls back to a generic message rather than showing a raw, possibly confusing exception message to the user.

## A specific UX decision: register immediately logs in
```typescript
// RegisterPage.tsx
await register(email, password, fullName)
// Register alone doesn't return a token (see M2.4/M2.5) — log in
// immediately with the same credentials so a successful signup lands
// the user in an authenticated session, not back at a login form.
await login(email, password)
navigate('/')
```
This bridges a real gap between the backend design (register and login are deliberately separate endpoints, M2.4) and what a user actually expects (sign up once, land inside the app) — the frontend absorbs that extra round trip so the user never has to fill out a login form immediately after just filling out a registration form.

## Why this pattern (controlled forms + local component state, not a form library)
For two simple forms with a handful of fields and no complex cross-field validation, a form library (Formik, React Hook Form) would add a dependency and abstraction for little benefit — plain `useState` per field is easy to read and exactly as much machinery as the problem needs. That calculus would change if forms grew significantly more complex (many fields, conditional fields, complex validation) — a case for reaching for a library, not a rule "never use one."

## Terms worth knowing
- **Controlled component**: a form input whose value is fully driven by React state, with every keystroke going through an `onChange` handler that updates that state — the opposite of an "uncontrolled" input that manages its own value internally, only read via a ref when needed.
- **Optimistic vs. pessimistic UI**: this flow is pessimistic — the button stays disabled and shows a loading state until the server actually responds, rather than assuming success immediately (contrast with M4.7's chat window, which does show the user's message optimistically before the server confirms it).

## If asked in an interview
> "Both auth forms are simple controlled components with local `useState` — no form library, since two forms with a handful of fields don't need one. The one deliberate UX decision worth calling out: since the register endpoint doesn't return a token by design (it's a separate concern from login), the register page calls `login()` immediately after a successful signup with the same credentials, so a new user lands in an authenticated session in one flow instead of hitting a second login form right after signing up."
