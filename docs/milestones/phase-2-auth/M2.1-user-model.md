# M2.1 — User Model & Migration

## One-line summary
The `users` table — the root of everything else that's per-person: submissions, conversations, progress.

## The problem
Before any auth flow can exist, there needs to be somewhere to persist a user record.

## What we built
`backend/app/models/user.py`:
```python
class User(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "users"

    email: Mapped[str] = mapped_column(unique=True, index=True)
    hashed_password: Mapped[str] = mapped_column()
    full_name: Mapped[str] = mapped_column()
```
Plus its Alembic migration, and it's imported in `backend/app/db/base.py`'s import chain so Alembic's autogenerate can see it (see M1.2 for why that import matters).

## How it works
- **`email: unique=True, index=True`** — two separate things doing two separate jobs. `unique=True` is a *database-level constraint*: Postgres itself rejects a second row with the same email, even if application code somehow forgot to check (defense in depth — `auth.py`'s `register()` relies on catching the resulting `IntegrityError` rather than only trusting an application-level pre-check, which would have a race condition: two near-simultaneous registrations with the same email could both pass a "does this email exist?" check before either has committed). `index=True` is a *performance* concern — email is looked up on every login, and without an index that's a full table scan.
- **`hashed_password`, never `password`** — the column name itself documents that plaintext is never stored (the actual hashing happens in M2.2's `security.py`).
- **No `role` or `is_admin` field yet** — this project has no admin/permissions tier; every authenticated user has the same capabilities. Worth noting as a real, current limitation rather than a design gap that was accidentally missed.

## Why a dedicated `User` model as the FK target for everything else
Nearly every other model in this project has a `user_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))` — `Conversation`, `ExerciseSubmission`, and (per the roadmap) future `LessonProgress`/`QuizAttempt`. `ondelete="CASCADE"` means deleting a user automatically deletes all their conversations, submissions, and progress at the database level — no orphaned rows left behind, and no need for application code to manually clean up every related table when a user is deleted.

## Terms worth knowing
- **Foreign key (FK)**: a column whose value must match a primary key in another table — the mechanism that links, e.g., an `ExerciseSubmission` row to the `User` who submitted it.
- **`ON DELETE CASCADE`**: a foreign key option telling the database "if the referenced row is deleted, delete this row too" — enforced by Postgres itself, not application code.
- **Unique constraint vs. application-level check**: a unique constraint is enforced by the database regardless of what the application does; an application-level "check if it exists first" query has a race-condition window between the check and the insert that a concurrent request could exploit.

## If asked in an interview
> "The `User` model is the FK target for basically every other per-person table — conversations, exercise submissions — all with `ON DELETE CASCADE`, so deleting a user cleans up everything they own at the database level, not via application cleanup code that could miss a table. Email uniqueness is enforced by a real database constraint, not just an application-level pre-check, specifically to close the race condition where two near-simultaneous signups with the same email could both pass a naive existence check before either commits."
