# M2.7 — Frontend Auth State & API Client

## One-line summary
A typed `fetch` wrapper that attaches the auth token to every request, plus a React context holding "who's logged in" for the whole app to read.

## The problem
Two frontend needs: (1) every API call needs the same boilerplate — build the URL, set headers, attach the token if present, parse errors consistently — and (2) many components across the app need to know "is someone logged in, and who," without prop-drilling that state through every layer of the component tree.

## What we built
- `frontend/src/api/client.ts` — `apiRequest<T>()`, plus token storage helpers and a typed `ApiError`
- `frontend/src/context/AuthContext.tsx` — `AuthProvider` + `useAuth()` hook

## How it works — the API client
```typescript
export async function apiRequest<T>(path: string, options: RequestInit = {}): Promise<T> {
  const headers = new Headers(options.headers)
  headers.set('Content-Type', 'application/json')
  const token = getStoredToken()
  if (token) headers.set('Authorization', `Bearer ${token}`)

  const response = await fetch(`${config.apiBaseUrl}${path}`, { ...options, headers })

  if (!response.ok) {
    const body = await response.json().catch(() => null)
    throw new ApiError(response.status, body?.error?.code ?? 'unknown_error',
                        body?.error?.message ?? 'Something went wrong')
  }
  if (response.status === 204) return undefined as T
  return response.json() as Promise<T>
}
```
Every API call in the app (`listCourses()`, `sendMessage()`, `submitExercise()` once M3.11 exists) is a thin wrapper around this one function, generic over `<T>` — the caller specifies the expected response shape and gets it back typed, e.g. `apiRequest<CourseSummary[]>('/courses')`. The token is read from `localStorage` on *every call*, not cached in a variable, so a login/logout elsewhere in the app takes effect on the very next request with no extra plumbing.

`ApiError` deliberately mirrors the backend's global error shape from M1.5 — `{status, code, message}` becomes a typed exception, so any calling component can do `err instanceof ApiError && err.code === 'email_taken'` instead of parsing a raw response body itself. This is the frontend half of the contract M1.5 established on the backend: one consistent error shape, understood by exactly one piece of code (`apiRequest`), reused everywhere.

## How it works — AuthContext
```typescript
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null)
  const [isLoading, setIsLoading] = useState(true)

  useEffect(() => {
    const token = getStoredToken()
    if (!token) { setIsLoading(false); return }
    apiRequest<User>('/auth/me')
      .then(setUser)
      .catch(() => clearStoredToken())
      .finally(() => setIsLoading(false))
  }, [])
  ...
}
```
On mount, if a token exists in `localStorage` (left over from a previous session), the app doesn't just *trust* it — it calls `GET /auth/me` to confirm the token is still valid and fetch fresh user data, because a stored token could be stale (expired, or the account deleted server-side, exactly the case M2.6's dependency guards against). Only a successful response populates `user`; a failed one clears the stale token.

`useAuth()` is a **custom hook** wrapping React's `useContext` — any component calls `const { user, login, logout } = useAuth()` to read or change auth state, without that state being passed down as props through every intermediate component (this is precisely the problem **React Context** solves — "prop drilling" avoidance for state many distant components need).

## Why this design
- **One `apiRequest` function, not `fetch()` calls scattered everywhere** — token attachment and error parsing are correct by construction everywhere, not something each new API call has to remember to do right.
- **Context over a global mutable variable**: React Context integrates with React's render cycle — when `setUser` runs, every component reading `useAuth()` automatically re-renders with the new value. A plain global variable wouldn't trigger UI updates at all.
- **Re-verifying via `/auth/me` on load, not trusting `localStorage` blindly**: closes the gap between "a token exists" and "a token is actually still valid," which matters because tokens expire (M2.3) and can't be revoked early.

## Terms worth knowing
- **React Context**: React's built-in mechanism for sharing state across a component tree without manually passing props down through every intermediate level.
- **Custom hook**: a function starting with `use` that wraps one or more of React's built-in hooks (`useState`, `useContext`, `useEffect`) into a reusable, named unit — `useAuth()` here.
- **Prop drilling**: passing a value through several layers of components that don't themselves need it, purely so a deeply nested component can receive it — the problem Context is designed to avoid.

## If asked in an interview
> "There's one `apiRequest` function every API call goes through — it attaches the bearer token from `localStorage` and parses the backend's error shape into a typed `ApiError` — so error handling and auth headers are consistent everywhere, not re-implemented per call site. `AuthContext` holds the current user in React state, and on app load it doesn't just trust a stored token — it calls `/auth/me` to confirm it's still valid, since a token can be expired or reference a deleted account."
