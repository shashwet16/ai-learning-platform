# M2.3 — JWT Utilities

## One-line summary
Issuing and verifying signed, tamper-proof, self-expiring login tokens — the mechanism that lets a user stay "logged in" across requests without the server storing session state.

## The problem
HTTP is stateless — the server doesn't inherently remember who made the last request. After a successful login, there needs to be *something* the client holds onto and sends with every subsequent request to prove "I'm still the same authenticated user." The two mainstream approaches are server-side sessions (a session ID the server looks up in a store) or a **JWT** (a signed token the client holds, requiring no server-side lookup at all).

## What we built
`backend/app/core/security.py` (extended from M2.2):
```python
def create_access_token(subject: str, expires_minutes=None) -> str:
    minutes = expires_minutes if expires_minutes is not None else settings.jwt_expire_minutes
    expire_at = datetime.now(UTC) + timedelta(minutes=minutes)
    payload = {"sub": subject, "exp": expire_at}
    return jwt.encode(payload, settings.jwt_secret, algorithm="HS256")

def decode_access_token(token: str) -> str:
    try:
        payload = jwt.decode(token, settings.jwt_secret, algorithms=["HS256"])
    except jwt.ExpiredSignatureError as exc:
        raise AppError("Token has expired", status_code=401, code="token_expired") from exc
    except jwt.PyJWTError as exc:
        raise AppError("Invalid token", status_code=401, code="invalid_token") from exc
    return payload["sub"]
```
Plus `backend/app/tests/test_jwt.py` covering: a valid round-trip, an expired token being rejected, and a tampered token being rejected.

## How it works
A JWT (JSON Web Token) has three base64url-encoded parts separated by dots: `header.payload.signature`. The payload here is `{"sub": "<user id>", "exp": <expiry timestamp>}` — `sub` (subject) is the standard JWT claim name for "who this token is about." The **signature** is an HMAC-SHA256 (`HS256`) of the header+payload, computed using `settings.jwt_secret` — a secret only the server knows. Anyone can *read* the payload (it's just base64, not encrypted) but only someone holding the secret can produce a signature that `jwt.decode` will accept as valid. Change even one character of the payload and the signature no longer matches — that's what makes the token tamper-evident, not tamper-*proof* in the sense of hiding data, but proof against undetected modification.

Because the token is **self-contained** — the user's identity and expiry are baked into the signed payload itself — validating it requires *zero database lookups*: `decode_access_token` alone tells you who the caller is and whether the token is still valid. This is the core trade-off vs. server-side sessions: no server-side session store to manage, but also no way to instantly revoke a single token before it naturally expires (there's no "delete this session" — a leaked token stays valid until `exp` passes; `jwt_expire_minutes` defaults to 30, which bounds that exposure window).

## A real bug this caught: a flaky tampered-token test
`test_decode_tampered_token_is_rejected` doesn't flip the token's *last* character — it deliberately flips a character in the *middle*, with a comment explaining a genuinely subtle finding:
> A JWT's trailing base64url character... can carry unused trailing bits that some decoders don't validate — flipping only that character occasionally leaves the decoded signature bytes unchanged, so the "tampered" token still verifies (confirmed empirically: ~6% false-negative rate across 200 trials).

Base64 encodes 3 bytes as 4 characters; when the input length isn't a multiple of 3, the final character's encoding has some bits that don't map to any real byte of the original data (padding bits). Flipping *only* those unused bits changes the base64 text without changing the decoded bytes — so a naive "flip the last char" test could pass by accident even if signature verification were subtly broken, because the actual signature bytes never changed. Flipping a mid-token character instead guarantees a real, decoded byte changes, making the test's failure mode meaningful. This was caught during **routine full-suite verification** of a later milestone (M4.6), not written correctly from the start — a good example of test quality itself needing scrutiny, not just application code.

## Why JWT (and not server-side sessions)
- **Stateless verification** fits a simple, single-backend-instance app well — no session store (Redis, a sessions table) to stand up and keep in sync.
- **Trade-off, stated honestly**: no instant token revocation. If this app needed "log out this device remotely" or "revoke a compromised token immediately," that would need either a short expiry + refresh-token rotation scheme, or a server-side blocklist — neither of which exists yet. Worth naming as a known limitation, not a gap that was missed.

## Terms worth knowing
- **JWT (JSON Web Token)**: a signed, self-contained token format for carrying claims (like user identity) between parties without a server-side lookup.
- **HMAC-SHA256**: the specific signing algorithm (`HS256`) used here — a symmetric scheme where the same secret both signs and verifies (as opposed to asymmetric schemes like RS256, which use a private/public key pair).
- **Claim**: a piece of data inside a JWT's payload — `sub` (subject) and `exp` (expiry) are both standard, reserved claim names.
- **Stateless auth**: authentication that requires no server-side record of "who's logged in" — the token itself carries everything needed to verify the request.

## If asked in an interview
> "Auth tokens are JWTs signed with HMAC-SHA256, carrying the user ID and an expiry claim — verifying a token is pure computation against a secret, no database lookup needed. The honest trade-off is no instant revocation: a leaked token stays valid until it naturally expires, which is why the expiry window is kept short. One genuinely interesting bug I found in testing: a tampered-JWT test that only flipped the token's last character had a real ~6% false-negative rate, because base64's final character can carry padding bits that don't affect the decoded bytes — flipping a mid-token character instead guarantees the test is actually exercising signature verification."
