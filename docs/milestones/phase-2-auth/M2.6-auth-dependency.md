# M2.6 — Auth Dependency & `/me` Endpoint

## One-line summary
`get_current_user` — the one reusable building block every protected route in the app depends on to know who's calling it.

## The problem
Every route that needs "the currently logged-in user" (submitting an exercise, sending a chat message, viewing `/auth/me`) needs the *same* logic: read the `Authorization` header, validate the JWT, look up the user, reject if any step fails. Writing that inline in every route would be repetitive and an easy place for one route to subtly diverge from the others' security behavior.

## What we built
`backend/app/api/deps.py`:
```python
bearer_scheme = HTTPBearer(auto_error=False)

def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(bearer_scheme),
    db: Session = Depends(get_db),
) -> User:
    if credentials is None:
        raise AppError("Not authenticated", status_code=401, code="not_authenticated")
    user_id = decode_access_token(credentials.credentials)
    user = db.execute(select(User).where(User.id == uuid.UUID(user_id))).scalar_one_or_none()
    if user is None:
        raise AppError("Not authenticated", status_code=401, code="not_authenticated")
    return user
```
And `GET /auth/me` in `auth.py` — the simplest possible consumer of it:
```python
@router.get("/me", response_model=UserRead)
def me(current_user: User = Depends(get_current_user)) -> User:
    return current_user
```

## How it works
`HTTPBearer` is FastAPI's built-in helper for the `Authorization: Bearer <token>` header pattern — it parses that header and hands the route the raw credentials. By default, if the header is entirely missing, `HTTPBearer` raises its own 403 automatically. `auto_error=False` disables that, and the code raises its own `401 not_authenticated` instead — done deliberately to match this project's convention (401 = "you're not authenticated," 403 would imply "you're authenticated but not allowed," a distinction this app treats consistently everywhere else).

`get_current_user` is a **FastAPI dependency**, meaning any route parameter typed as `current_user: User = Depends(get_current_user)` gets this exact logic run automatically before the route body executes — see it reused verbatim in `exercises.py`'s `submit_exercise`/`list_submissions` and `chat.py`'s `send_message`/`list_conversations`. This is dependency composition: `get_current_user` itself depends on `get_db` and `bearer_scheme`, and FastAPI resolves the whole chain automatically.

Note the third failure mode covered: even a *validly signed, non-expired* token becomes invalid if the user it names was deleted after the token was issued — `user is None` after the lookup catches that, returning the same generic `not_authenticated` rather than a different message that would hint at the reason.

## Why a shared dependency (and not a decorator, or manual checks per route)
- **One place enforces the security contract.** If this logic needs to change (e.g. adding a "user is banned" check later), it changes in one function and every protected route picks it up automatically.
- **Declarative, not imperative**: a route's signature (`current_user: User = Depends(get_current_user)`) documents "this route requires auth" just by being read — no need to trace into the function body to discover an auth check buried partway through.
- **Testable in isolation**: the dependency can be tested/mocked independently of any specific route.

## Terms worth knowing
- **Bearer token**: an access token sent in the `Authorization: Bearer <token>` HTTP header — "bearer" meaning whoever holds (bears) the token can use it, with no additional proof of identity required.
- **401 vs. 403**: 401 Unauthorized means "you haven't proven who you are" (missing/invalid credentials); 403 Forbidden means "you're known, but not allowed to do this." This project treats every auth failure as 401, since there's no permission tier yet (see M2.1's note on no roles existing).
- **Dependency composition**: FastAPI dependencies can themselves depend on other dependencies, and the framework resolves the whole graph automatically per request.

## If asked in an interview
> "`get_current_user` is a single FastAPI dependency that every protected route shares — it validates the bearer token, decodes it, and re-fetches the user from the database on every request, rather than trusting the token's claims alone. That last part matters: a validly-signed token for a since-deleted user still gets rejected, because the lookup returns nothing — the token being cryptographically valid isn't the same as the account it names still existing."
