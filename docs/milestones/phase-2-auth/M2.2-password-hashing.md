# M2.2 — Password Hashing Utility

## One-line summary
Passwords are never stored — only a one-way bcrypt hash of them, so a stolen database still doesn't reveal anyone's actual password.

## The problem
If a database is ever breached (misconfiguration, SQL injection, an insider, a backup left somewhere public), storing plaintext passwords means every user's real password is instantly exposed — and because people reuse passwords across sites, that breach cascades into every other account that user has, everywhere. The mitigation is: never store the password at all, only proof that someone *knew* it.

## What we built
`backend/app/core/security.py`:
```python
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(password: str, hashed_password: str) -> bool:
    return pwd_context.verify(password, hashed_password)
```
Plus `backend/app/tests/test_security.py` — pytest coverage confirming: correct password verifies true, wrong password verifies false, the stored value is never the plaintext, and hashing the same password twice produces two *different* hashes.

## How it works
A **hash function** turns input of any length into a fixed-size output, deterministically (same input always gives the same output) but is computationally infeasible to reverse. bcrypt specifically is a **password hashing algorithm** — distinct from a general-purpose hash like SHA-256 — designed to be deliberately *slow* and tunable-slower over time as hardware gets faster (a "cost factor" baked into the algorithm), which directly defeats brute-force guessing: an attacker with a stolen hash can't just try billions of guesses per second the way they could against a fast general-purpose hash.

`hash_password(password) != hash_password(password)` for the *same* input — this is intentional, not a bug, and the test suite explicitly asserts it. bcrypt generates a random **salt** per call and bakes it into the output string alongside the hash itself. Without a salt, two users with the same password would have identical hashes, and an attacker could precompute a lookup table (a "rainbow table") of common password → hash pairs once and use it against every stolen database ever. A random salt makes that precomputation useless — each hash needs its own attack from scratch.

`verify_password` doesn't need the salt passed separately — bcrypt's output format embeds the salt in the hash string itself, so `verify_password` can extract it and re-derive the same hash to compare.

## Why bcrypt (and not SHA-256, or storing plaintext)
- **Plaintext**: catastrophic on any breach, as above — never acceptable.
- **A fast general-purpose hash (MD5/SHA-256) alone**: technically one-way, but *fast* — modern GPUs can compute billions of SHA-256 hashes per second, making brute-force/dictionary attacks against a stolen hash database practical. Password hashing needs to be slow *on purpose*.
- **bcrypt specifically**: mature, widely audited, has salting built in, and its cost factor can be increased over time without changing the API — `deprecated="auto"` in `CryptContext` means if the scheme list is ever extended with a newer algorithm, `verify_password` can still validate old bcrypt hashes while new ones use the newer scheme.

## Terms worth knowing
- **Hashing**: a one-way transformation — computationally easy to compute forward, effectively impossible to reverse.
- **Salt**: random data mixed into a password before hashing so identical passwords don't produce identical hashes, defeating precomputed lookup-table attacks.
- **Cost factor / work factor**: a tunable parameter making a hash algorithm deliberately slower to compute, scaled up over the years to stay ahead of faster hardware.
- **Rainbow table**: a precomputed table mapping common passwords to their hash output, used to reverse unsalted hashes instantly by lookup instead of brute force.
