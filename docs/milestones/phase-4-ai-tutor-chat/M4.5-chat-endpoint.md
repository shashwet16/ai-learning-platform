# M4.5 — Chat Endpoint

## One-line summary
`POST /chat/{conversation_id}/messages` — send a message, get a real AI reply back, with both persisted; a get-or-create design since there's no separate "start a conversation" endpoint.

## The problem
Tie everything from M4.1–M4.4 together into one working round trip: a user sends text, the full conversation history plus that new message goes to the configured LLM provider, and both the user's message and the assistant's reply get saved.

## What we built
```python
@router.post("/{conversation_id}/messages", response_model=MessageRead, status_code=201)
def send_message(conversation_id, body, current_user=Depends(get_current_user), db=Depends(get_db)):
    conversation = db.get(Conversation, conversation_id)
    if conversation is None:
        conversation = Conversation(id=conversation_id, user_id=current_user.id)
        db.add(conversation)
        db.flush()
    elif conversation.user_id != current_user.id:
        raise AppError("Conversation not found", status_code=404, code="conversation_not_found")

    user_message = Message(conversation_id=conversation.id, role="user", content=body.content)
    db.add(user_message)
    db.commit()

    history = db.scalars(select(Message).where(Message.conversation_id == conversation.id)
                          .order_by(Message.created_at)).all()
    chat_messages = [{"role": m.role, "content": m.content} for m in history]

    provider = get_llm_provider()
    reply_text = provider.generate(chat_messages)

    assistant_message = Message(conversation_id=conversation.id, role="assistant", content=reply_text)
    db.add(assistant_message)
    db.commit()
    db.refresh(assistant_message)
    return assistant_message
```

## How it works — get-or-create
There's no separate `POST /chat/conversations` "create a new conversation" endpoint anywhere in the roadmap. So this single endpoint has to serve both "start a brand-new conversation" and "continue an existing one" — decided purely by whether `conversation_id` (supplied by the *caller*, notably — see M4.7's frontend, which generates a UUID client-side with `crypto.randomUUID()`) already exists in the database. If it doesn't, one gets created on the spot (`db.add(conversation); db.flush()` — `flush()`, not `commit()`, sends the INSERT to the database so `conversation.id` is usable for the message insert that follows, without yet closing out the transaction). If it does exist, ownership is checked before anything else happens.

**Ownership check returns 404, not 403** — deliberately, with the exact same reasoning as M2.5's login endpoint: don't confirm to a caller that a conversation ID belonging to someone else exists at all. A 403 would leak "this resource exists, you're just not allowed to see it"; 404 is indistinguishable from "this ID was never used by anyone."

## How it works — building the LLM call
`history` re-fetches *every* message in the conversation (including the user message just inserted) in chronological order, then converts each ORM `Message` row into M4.1's `ChatMessage` dict shape. This is what gives the LLM real **multi-turn context** — every call to `provider.generate()` includes the entire conversation so far, not just the latest message, so the model can reference earlier turns. The trade-off, not yet addressed anywhere in the roadmap: this resends the *whole* history on every single message, which grows linearly with conversation length and will eventually hit context-window/token-cost limits on a long-running conversation — a real, known scaling concern for a later milestone, not something this implementation silently gets wrong so much as defers.

Two separate `db.commit()` calls, not one: the user's message is committed *before* calling `provider.generate()`. This matters — if the LLM call fails or times out after that commit, the user's message is still safely persisted (they don't lose what they typed), even though no assistant reply exists yet.

## Why this design (single get-or-create endpoint, full-history resend) over the alternatives
- **Get-or-create avoids a redundant endpoint**: a separate "create conversation" call would just be an empty conversation with no messages yet — this design collapses "create" and "first message" into the same natural action a user actually takes (typing something and hitting send).
- **Full-history resend is the simplest correct thing that works today**: this app has no conversation-summarization or sliding-window-truncation logic yet — sending everything is correct (the model sees full context) even though it isn't the most efficient design forever.

## Terms worth knowing
- **Get-or-create**: a common API pattern where an endpoint transparently creates a resource if it doesn't exist yet, rather than requiring the caller to check existence and choose between two different endpoints.
- **Multi-turn context**: giving an LLM the full prior conversation on each call so it can reference earlier turns — as opposed to treating each message as an isolated, context-free prompt.
- **`flush()` vs. `commit()`**: `flush()` sends pending changes to the database (making generated values like a UUID's server-assigned defaults available) without ending the transaction; `commit()` ends the transaction, making the changes permanent and visible to other connections.

## If asked in an interview
> "The endpoint is a get-or-create on `conversation_id` — the client generates the UUID, and whether that ID already exists in the database decides whether this call starts a new conversation or continues one, since the roadmap never called for a separate 'create conversation' endpoint. Every call resends the full conversation history to the LLM for real multi-turn context, which I'll flag honestly as a known scaling limit — it grows linearly with conversation length and would need trimming or summarization for long-running chats, but it's the simplest correct thing for the current scope. I also deliberately commit the user's message before calling the LLM, so a failed or slow provider call never loses what the user actually typed."
