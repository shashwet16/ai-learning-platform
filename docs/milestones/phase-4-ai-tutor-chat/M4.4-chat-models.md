# M4.4 — Chat Conversation & Message Models

## One-line summary
`Conversation` and `Message` tables — persistent chat history per user, and the source of a real Postgres-enum migration bug caught and fixed.

## The problem
A chat feature needs to remember what was said. Without persistence, refreshing the page (or the roadmap's own stated goal — "resume/view past chats," M4.6) would be impossible; every conversation would only ever exist in memory for the duration of one page load.

## What we built
`backend/app/models/chat.py`:
```python
class Conversation(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "conversations"
    user_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
    messages: Mapped[list["Message"]] = relationship(
        back_populates="conversation", cascade="all, delete-orphan", order_by="Message.created_at")

class Message(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "messages"
    conversation_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("conversations.id", ondelete="CASCADE"))
    role: Mapped[str] = mapped_column(SQLEnum("user", "assistant", name="message_role"))
    content: Mapped[str] = mapped_column(Text)
    conversation: Mapped["Conversation"] = relationship(back_populates="messages")
```

## How it works
This mirrors the `Course`/`Module`/`Lesson` parent-child pattern from M3.1 exactly — `Conversation` is the parent, `Message` the child, linked by `conversation_id`, ordered by `Message.created_at` via the relationship's `order_by`, with `ON DELETE CASCADE` both at the FK level and via `cascade="all, delete-orphan"` — deleting a conversation deletes its messages, deleting a user (M2.1) deletes all their conversations and therefore all their messages, transitively.

`role: Mapped[str] = mapped_column(SQLEnum("user", "assistant", name="message_role"))` uses a **Postgres enum type** — not a plain string column with application-level validation. This means the *database itself* rejects an attempt to insert a `Message` with `role="moderator"` or any value outside `{"user", "assistant"}`, as a hard schema-level constraint — a stronger guarantee than a Python-side check, which could be bypassed by a bug elsewhere or a direct SQL write.

## The real migration bug: dropping an enum's column doesn't drop the enum type
This is the concrete example referenced in M1.2's doc. When this migration's `downgrade()` was auto-generated, it likely only contained `op.drop_column('messages', 'role')` (or dropped the whole `messages` table, which drops the column too) — but Postgres enum types (`CREATE TYPE message_role AS ENUM (...)`) are **separate named database objects**, independent of any column that happens to use them. Dropping the column (or even the table) does not drop the type — it's still registered in the database's catalog afterward. Re-running the migration's `upgrade()` after that incomplete `downgrade()` then fails, because `CREATE TYPE message_role` collides with the type that never actually got removed. The fix required a manual addition to `downgrade()`: an explicit statement to drop the enum type itself, in addition to whatever table-level cleanup autogenerate produced. This is a genuinely well-known Alembic/Postgres gotcha worth having a real, concrete example of — not just abstract advice.

## Why store the raw conversation as `role` + `content` rows (and not, say, a single JSON blob per conversation)
- **Queryable per message**: `list_submissions`-style queries (M4.6's `GET /chat/{id}/messages`) can filter/order/paginate at the row level — a JSON blob would require loading and parsing the whole conversation just to read the last N messages.
- **Matches the shape LLM APIs actually expect**: converting rows to `list[ChatMessage]` (M4.1's type) for `provider.generate()` is a straightforward `SELECT ... ORDER BY created_at` plus a list comprehension (see M4.5) — a JSON-blob storage format would need its own serialization scheme to get back to that same shape.

## Terms worth knowing
- **Database enum type**: a Postgres-level named type restricting a column to a fixed, explicit set of values — enforced by the database engine itself, distinct from an application-level `Literal["user", "assistant"]` type hint, which only helps at the Python/type-checker level.
- **Schema-level constraint vs. application-level validation**: a schema-level constraint (like this enum, or M2.1's unique email) can't be bypassed by any code path, including ones a developer forgot to add validation to; application-level validation only protects the specific code paths that actually call it.
