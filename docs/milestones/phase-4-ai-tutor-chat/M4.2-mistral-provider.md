# M4.2 — Mistral Provider Implementation (planned: Anthropic)

## One-line summary
The first real, working LLM backend — and a concrete, live demonstration that M4.1's provider-agnostic design actually works: a full vendor substitution with zero changes to the interface.

## The problem
`LLMProvider` (M4.1) is just a contract with no implementation. Something has to actually call a real LLM API and return real text.

## What we actually built
`backend/app/services/llm/mistral_provider.py`:
```python
class MistralProvider(LLMProvider):
    def __init__(self, model: str = "mistral-small-latest") -> None:
        if not settings.mistral_api_key:
            raise RuntimeError("MISTRAL_API_KEY is not set — required to use MistralProvider.")
        self._client = Mistral(api_key=settings.mistral_api_key)
        self._model = model

    def generate(self, messages: list[ChatMessage]) -> str:
        response = self._client.chat.complete(model=self._model, messages=list(messages))
        content = response.choices[0].message.content
        if not isinstance(content, str):
            raise RuntimeError("Mistral API returned non-text content; expected a plain string.")
        return content
```
Plus `MISTRAL_API_KEY` added to `config.py` and `.env.example`, and the `mistralai` SDK added as a dependency.

## The deviation, and why it's worth understanding rather than glossing over
The roadmap originally called for `AnthropicProvider`. It became `MistralProvider` instead, for one concrete, practical reason: **no Anthropic API key was available**. This is documented explicitly, not hidden — the roadmap even carries a note-to-self ("An `AnthropicProvider` can still be added later as an additional `LLMProvider` implementation without changing anything else") confirming the substitution didn't compromise the design goal at all.

This is the practical payoff of M4.1's abstraction, made concrete: the chat route, the provider factory (M4.3), and every call site depend only on `LLMProvider.generate(messages) -> str` — none of them know or care that the concrete class is `MistralProvider` rather than `AnthropicProvider`. Swapping vendors meant writing one new file matching the existing interface shape and registering it in the factory — not touching `chat.py`, not touching any route, not touching any test that mocks the interface rather than a specific vendor.

## How it works
- **Fail-fast on missing config, at the point of actual use, not at import time.** The `RuntimeError` check for `mistral_api_key` happens inside `__init__`, when a `MistralProvider` is actually instantiated — not at module import. This matters because `config.py`'s `mistral_api_key: str | None = None` is *optional* (M0.5) — the whole app must still start without it, since nothing calls an LLM provider until a chat request actually arrives (M4.5). If the check were at import time or made the setting required, the entire backend would refuse to boot for developers not currently working on the chat feature.
- **A defensive type check on the response** — `if not isinstance(content, str): raise RuntimeError(...)`. LLM SDKs can technically return non-text content in some response modes (tool calls, multi-part content); this guards the `LLMProvider` contract's promise (`generate` always returns `str`) rather than letting an unexpected shape silently propagate as a type error somewhere else, further from its actual cause.

## Why Mistral specifically, given the constraint
Mistral offers a straightforward, well-documented chat completion API with an available free tier — a pragmatic choice when the originally planned vendor's credential wasn't available, and one that didn't require compromising the project's provider-agnostic requirement at all, precisely because that requirement was designed in from M4.1 rather than retrofitted.

## Terms worth knowing
- **Vendor lock-in (and how this project avoids it)**: designing business logic against a vendor's specific SDK/API shape directly, making a future switch expensive. The abstraction from M4.1 is the direct antidote — this milestone is proof it works, not just a design claim.
- **Fail fast vs. optional-until-used**: a required setting (M0.5's `database_url`) fails the whole app at startup if missing; an optional-until-used setting (`mistral_api_key`) only fails when the specific feature depending on it is actually invoked — the right choice depends on whether the app has any legitimate reason to run without that feature.

## If asked in an interview
> "The plan was to use Anthropic first, but no API key was available, so I implemented `MistralProvider` against the exact same `LLMProvider` interface instead — a genuinely clean substitution with zero changes anywhere else in the codebase, which is really the whole point of designing that interface before any concrete implementation existed. It's a good real example of a provider-agnostic architecture actually earning its cost, not just being a nice idea on paper."
