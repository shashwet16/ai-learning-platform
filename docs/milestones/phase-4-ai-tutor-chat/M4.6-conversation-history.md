# M4.6 — Conversation History Endpoint

## One-line summary
`GET /chat/conversations` and `GET /chat/{id}/messages` — resuming and viewing past chats, both correctly scoped so one user can never see another's conversation.

## The problem
M4.5 lets a user send messages, but nothing yet lets the frontend list a user's past conversations or reload one's full message history — needed for M4.7's chat UI to show anything on page load rather than starting blank every time.

## What we built
```python
@router.get("/conversations", response_model=list[ConversationRead])
def list_conversations(current_user=Depends(get_current_user), db=Depends(get_db)):
    return list(db.scalars(select(Conversation)
        .where(Conversation.user_id == current_user.id)
        .order_by(Conversation.created_at.desc())).all())

@router.get("/{conversation_id}/messages", response_model=list[MessageRead])
def get_conversation_messages(conversation_id, current_user=Depends(get_current_user), db=Depends(get_db)):
    conversation = db.get(Conversation, conversation_id)
    if conversation is None or conversation.user_id != current_user.id:
        raise AppError("Conversation not found", status_code=404, code="conversation_not_found")
    return list(db.scalars(select(Message)
        .where(Message.conversation_id == conversation_id)
        .order_by(Message.created_at)).all())
```

## How it works
Both endpoints require `get_current_user` (M2.6) and filter *at the query level* by `current_user.id` — `list_conversations` only ever selects rows `WHERE user_id == current_user.id`, so there's no way for the returned list to include another user's conversations even by accident; the ownership boundary is enforced in the `SELECT`, not by filtering results after the fact in Python. `get_conversation_messages` repeats the same `conversation is None or conversation.user_id != current_user.id` check used in M4.5's `send_message` — checking ownership *before* returning any messages, and again returning 404 (not 403) for someone else's conversation ID, for the identical "don't confirm existence" reasoning covered in M4.5 and M2.5.

`list_conversations` orders by `created_at.desc()` — most recent conversation first, matching how a "resume a past chat" list should read (newest at the top, not oldest).

## A real bug found here, unrelated to this milestone's own feature
The roadmap's progress notes are specific: "M4.6 also fixed a genuinely flaky JWT tampering test from M2.3 (~6% false-negative rate) found during routine full-suite verification." This is worth understanding as a pattern, not just a footnote: **verifying one milestone by running the full test suite surfaced a real, pre-existing bug in a completely unrelated, already-shipped milestone.** That's the payoff of "run the whole suite," not just the tests for what you just touched — a flaky test sitting quietly in the suite for three milestones only got caught because routine verification happened to trigger its ~6% failure rate on that particular run. (The bug itself — a JWT tamper-test flipping only the token's last base64 character, which can occasionally leave decoded bytes unchanged — is explained in full in M2.3's own doc.)

## Why ownership-scoped queries (not "fetch everything, then filter in Python")
Filtering at the SQL `WHERE` clause level, rather than fetching broader data and filtering in application code afterward, means there's no intermediate state where unauthorized data ever exists in memory in the request at all — a smaller, more auditable surface for a privacy bug to hide in, and it's also simply more efficient (the database does less work returning rows that would just be discarded).

## Terms worth knowing
- **Authorization scoping at the query level**: encoding "who is allowed to see this" directly into the database query's filter conditions, rather than as a separate check applied to already-fetched data.
- **Flaky test**: a test that sometimes passes and sometimes fails against the same, unchanged code — usually a sign the test (or the thing it's testing) depends on some non-deterministic factor the test doesn't fully control for. See M2.3 for the specific root cause found here.
