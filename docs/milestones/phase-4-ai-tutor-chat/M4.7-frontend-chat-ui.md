# M4.7 — Frontend Chat UI

## One-line summary
A real, usable tutor chat in the browser — optimistic message display, a persistent conversation across reloads, and a loading state while waiting on the AI.

## The problem
Everything from M4.1–M4.6 is a working backend with no UI. This milestone builds the actual chat experience: a message thread, an input box, and the round trip between them.

## What we built
`frontend/src/pages/ChatPage.tsx`, `frontend/src/components/ChatWindow.tsx`, `frontend/src/api/chat.ts`.

## How it works — a stable conversation ID across reloads
```typescript
function getOrCreateConversationId(): string {
  const stored = localStorage.getItem(CONVERSATION_ID_STORAGE_KEY)
  if (stored) return stored
  const fresh = crypto.randomUUID()
  localStorage.setItem(CONVERSATION_ID_STORAGE_KEY, fresh)
  return fresh
}

export function ChatPage() {
  const [conversationId] = useState(getOrCreateConversationId)
  return <ChatWindow conversationId={conversationId} />
}
```
The **frontend generates the conversation UUID**, not the backend — this is the client side of M4.5's get-or-create design: the first time a message is sent with a fresh UUID, the backend creates the conversation on the spot; every reload after that reuses the same stored ID from `localStorage`, so refreshing the page resumes the same conversation instead of silently starting a new, empty one. `useState(getOrCreateConversationId)` — passing the function itself, not calling it (`useState(getOrCreateConversationId())` would be wrong) — is React's "lazy initializer" pattern, guaranteeing the function only runs once on the component's first render, not on every re-render.

## How it works — optimistic UI
```typescript
const optimisticMessage: MessageRead = {
  id: `optimistic-${Date.now()}`, role: 'user', content, created_at: new Date().toISOString(),
}
setMessages((prev) => [...(prev ?? []), optimisticMessage])
setIsSending(true)
try {
  const assistantMessage = await sendMessage(conversationId, content)
  setMessages((prev) => [...(prev ?? []), assistantMessage])
} catch (err) { ... } finally { setIsSending(false) }
```
The user's own message appears in the thread **immediately**, before the network request to the backend even resolves — with a comment explaining why: "the round trip to Mistral can take a couple of seconds, and there's no reason to delay showing what they just typed." This is **optimistic UI** — assuming the simple, common case (the message sends fine) will succeed, and showing that result immediately rather than waiting for server confirmation first. Contrast with M2.8's auth forms, which are deliberately *pessimistic* (button stays disabled until the server actually responds) — the right choice differs by context: a login attempt can genuinely fail in a way the user needs to see before proceeding (wrong password), while a chat message being *displayed* doesn't depend on whether the *AI's reply* succeeds.

A `"Thinking…"` placeholder bubble renders while `isSending` is true, and a `threadEndRef` + `scrollIntoView({ behavior: 'smooth' })` effect keeps the newest message in view automatically.

## A benign 404 turned into a normal empty state
```typescript
.catch((err) => {
  // A freshly generated conversation ID has no conversation row on the
  // backend yet — it's only created on the first POST (M4.5's get-or-
  // create). A 404 here just means "no history yet," not a real failure.
  if (err instanceof ApiError && err.code === 'conversation_not_found') {
    setMessages([])
  } else {
    setError(...)
  }
})
```
This is a good example of a frontend needing to understand *why* the backend can return a given error, not just what the error is. `GET /chat/{id}/messages` for a brand-new conversation ID (nothing sent yet) legitimately 404s, per M4.6's implementation — because from the backend's perspective, that conversation genuinely doesn't exist until the first message creates it. The frontend distinguishes this specific, expected 404 (`conversation_not_found`, on first load) from any other failure, treating it as "empty history" rather than an error banner — a wrong or missing distinction here would show a scary error message to every first-time chat user, which would be a bad first impression for a case that's actually completely normal.

## Terms worth knowing
- **Optimistic UI**: updating the interface to reflect an action's expected outcome immediately, before the server has actually confirmed it — chosen when the action is very likely to succeed and the cost of a rare rollback is low.
- **Lazy initializer (React)**: passing a function (not its result) to `useState`, so React only invokes it once, on the component's first render — avoids re-running expensive or side-effecting setup logic on every re-render.
