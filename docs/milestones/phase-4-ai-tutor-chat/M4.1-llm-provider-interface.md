# M4.1 — LLM Provider Interface

## One-line summary
An abstract contract (`LLMProvider.generate(messages) -> str`) that lets the rest of the app call "an LLM" without knowing or caring which vendor is actually behind it — the single most important architectural decision in the chat feature.

## The problem
LLM vendors (Anthropic, OpenAI, Mistral, ...) each have their own SDK, request/response shape, and authentication scheme. Writing chat route code directly against one vendor's SDK means every future model swap, every fallback-to-a-different-provider decision, and every "let's A/B test two models" experiment requires editing the actual business logic — not just configuration.

## What we built
`backend/app/services/llm/base.py`:
```python
class ChatMessage(TypedDict):
    role: Literal["user", "assistant", "system"]
    content: str

class LLMProvider(ABC):
    @abstractmethod
    def generate(self, messages: list[ChatMessage]) -> str:
        raise NotImplementedError
```

## How it works
This is the **Strategy pattern** (or, viewed from the DI angle, **dependency inversion**): the chat route (M4.5) depends only on this abstract interface, never on a concrete vendor class. `ABC` (Abstract Base Class) + `@abstractmethod` means Python itself enforces that any concrete subclass (`MistralProvider`, a future `AnthropicProvider`) *must* implement `generate` — attempting to instantiate a subclass that doesn't would raise a `TypeError` at instantiation time, not silently produce a broken object.

`ChatMessage` is deliberately its own type, named to avoid confusion with the future `Message` *ORM* model (M4.4) — a `ChatMessage` is a plain dict shape describing "one turn in the conversation," used purely to pass data to a provider; it never touches the database. This distinction matters because `chat.py`'s route code has to convert *between* the two: database `Message` rows become a `list[ChatMessage]` right before calling `provider.generate(...)` (see M4.5).

The comment on the class itself states the discipline directly: "No vendor-specific code belongs in this file." Every file in `services/llm/` other than `base.py` and `factory.py` is where vendor-specific code is *allowed* to live — `base.py` stays permanently vendor-neutral.

## Why build this abstraction *before* implementing any real provider
This milestone shipped with literally zero runtime behavior — its own "how to test it" note says "code review only... no runtime behavior yet." That's intentional: designing the seam *before* the first real implementation forces the interface to be genuinely minimal and provider-agnostic, rather than accidentally shaped around one vendor's SDK quirks (which is what tends to happen if you write the concrete implementation first and "extract an interface" afterward — the interface ends up leaking vendor-specific assumptions). This exact discipline is what made M4.2's actual substitution (Mistral instead of the originally planned Anthropic, due to API key availability) a clean drop-in rather than a rewrite — see that milestone's doc.

## Terms worth knowing
- **Strategy pattern**: a design pattern where interchangeable algorithms/implementations (here: different LLM vendors) share a common interface, letting calling code swap between them without changing its own logic.
- **Dependency inversion**: high-level code (the chat route) depends on an abstraction (`LLMProvider`), and low-level concrete implementations (`MistralProvider`) depend on that same abstraction — neither depends directly on the other.
- **Abstract Base Class (ABC) / abstract method**: Python's mechanism for defining a class that can't be instantiated directly and requires subclasses to implement specific methods, enforced at the language level rather than just by convention/documentation.

## If asked in an interview
> "Before writing any real LLM integration, I defined a single abstract `LLMProvider.generate(messages) -> str` interface with zero vendor-specific code in it — no runtime behavior in this milestone at all, just the contract. That paid off almost immediately: when Anthropic wasn't actually available (no API key), swapping in Mistral instead was a same-shape drop-in implementation, not a rewrite of the chat feature, because the route code never depended on anything vendor-specific to begin with."
