# M4.3 — Provider Factory

## One-line summary
`get_llm_provider()` — one function that returns whichever provider is configured, selected by an env var, so no call site ever hardcodes a vendor class name.

## The problem
Even with `LLMProvider` as an abstract interface (M4.1) and a concrete `MistralProvider` (M4.2), *something* still has to decide which concrete class to instantiate. Hardcoding `MistralProvider()` directly in the chat route would re-introduce exactly the coupling the interface was built to avoid — switching providers would mean editing route code again.

## What we built
`backend/app/services/llm/factory.py`:
```python
_PROVIDERS: dict[str, type[LLMProvider]] = {
    "mistral": MistralProvider,
    "fake": FakeProvider,
}

def get_llm_provider() -> LLMProvider:
    try:
        provider_cls = _PROVIDERS[settings.llm_provider]
    except KeyError:
        raise ValueError(f"Unknown LLM_PROVIDER {settings.llm_provider!r}. "
                          f"Registered providers: {sorted(_PROVIDERS)}") from None
    return provider_cls()
```
Plus `llm_provider: str = "mistral"` in `config.py` (M0.5's typed settings pattern, reused).

## How it works
`_PROVIDERS` is a **registry** — a dict mapping a plain string name to a *class* (not an instance) — `type[LLMProvider]` is the type annotation for "a class that is (a subclass of) `LLMProvider`," as opposed to `LLMProvider` itself which would mean "an instance of it." `get_llm_provider()` looks up the configured name, and only instantiates the class (`provider_cls()`) at the point of actual use — this is why `MistralProvider.__init__`'s fail-fast check (M4.2) fires exactly when a caller asks for a provider, not any earlier.

Note where the registry itself lives: `config.py`'s `llm_provider` field is a plain `str`, not a `Literal["mistral", "fake"]` — deliberately, per its own comment ("the factory module... is the single place that owns the actual registry, so config.py doesn't need to know every provider name"). This avoids duplicating the list of valid provider names in two places that would need to stay in sync — `config.py` just validates "is this a string," and `factory.py` is the sole authority on which strings are actually meaningful, raising its own clear `ValueError` (naming every registered option) if the configured name doesn't match anything.

A second provider, `FakeProvider`, is also registered here — worth noting it wasn't originally scoped for this milestone at all. The roadmap explicitly flags: "M4.3 also added a `FakeProvider`... since the milestone's own test method needed a second registered provider to toggle against." M4.3's own acceptance test ("toggle the env var between two registered provider names, confirm the factory returns the matching class each time") can't be meaningfully verified with only one registered provider — there'd be nothing to toggle *to*. Building `FakeProvider` here, ahead of its originally planned milestone (M7.4, for offline chat tests), was a pragmatic pull-forward once the actual need became concrete.

## Why a factory function + string-keyed registry (and not, say, `if/elif` chains, or importing the concrete class directly wherever needed)
- **One switch point**: adding a real `AnthropicProvider` later means one new dict entry in `factory.py` — nothing else in the app changes.
- **Config-driven, not code-driven**: switching providers in any environment (dev vs. staging vs. prod, or A/B testing two models) is an environment variable change, not a code deploy.
- **A single, clear failure mode for typos**: an unrecognized `LLM_PROVIDER` value fails immediately with a `ValueError` naming every valid option — much clearer than a silent fallback or a deep `AttributeError` from trying to use a `None`.

## Terms worth knowing
- **Factory pattern**: a function or method whose job is to construct and return an object, deciding *which* concrete type to construct based on some input (here, a config string) — the calling code never names the concrete class itself.
- **Registry**: a lookup table (often just a dict) mapping names/keys to implementations, letting new implementations be added by registering them rather than by branching logic that needs to be found and edited.

## If asked in an interview
> "The factory is a small dict-based registry mapping a config string to a provider class, instantiated lazily on each call — so switching providers is an environment variable change, and adding a new vendor later is one new registry entry, not a hunt through the codebase for hardcoded class references. It also ended up being where `FakeProvider` was born, a milestone earlier than planned, because the factory's own acceptance test genuinely needed a second provider to toggle against to be meaningful — a good small example of letting a test's real requirements pull a decision forward rather than rigidly following the original plan."
