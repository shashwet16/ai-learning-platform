# M7.3 — Quiz & Grading Tests (quiz half)

## One-line summary
16 tests locking in quiz fetching, MCQ grading, and LLM-graded free text — including the one assertion that actually matters for a quiz system: that fetching a quiz never leaks the answer key.

## Status
**Partially complete.** M7.3 as scoped covers both `test_courses.py` and `test_quizzes.py`. This milestone delivered the quiz half (`test_quizzes.py`, plus `test_grading.py` for the grading service underneath it). `test_courses.py` is still outstanding.

## The problem
Phase 5 shipped quizzes with grading logic that had only ever been checked by hand — a few `curl` calls at the moment each endpoint was written, against a live Mistral API. That leaves three specific risks:

1. **The answer key.** `GET /lessons/{id}/quiz` must serve questions and choices while withholding `is_correct`. That's enforced by `is_correct` simply being absent from `ChoiceRead` — a safety property that holds by omission, which is exactly the kind of property a future refactor breaks silently. Nothing would fail. The quiz would just quietly start shipping its own answers.
2. **Grading arithmetic.** `correct_count` / `graded_count` has a deliberate subtlety: unanswered questions must be `correct=None` and stay *out of the denominator*, so an unattempted question doesn't count against the learner.
3. **Cost and flakiness.** Open-ended grading calls a real LLM. Tests that hit it would be slow, non-deterministic, and would spend money on every run.

## What we built
- **`app/tests/test_quizzes.py`** — 10 route tests
- **`app/tests/test_grading.py`** — 6 unit tests for `grade_open_ended()`

## How it works

### The answer-key test
```python
def test_get_quiz_never_leaks_the_answer_key(client, lesson, quiz):
    response = client.get(f"/lessons/{lesson.id}/quiz")
    assert "is_correct" not in response.text
    for choice in response.json()["questions"][0]["choices"]:
        assert set(choice) == {"id", "text", "order"}
```
Two assertions, deliberately overlapping. The first is a substring check against the **raw response text**, not the parsed model — so it catches the field appearing anywhere, under any nesting, even somewhere I didn't think to look. The second pins the exact key set, so it catches *any* new field, not just the one known to be dangerous today. A test that only checked `"is_correct" not in choice` would pass while a future `answer_explanation` field leaked.

### Grading without the network
`get_llm_provider()` is called directly inside the route, not injected via `Depends`, so `app.dependency_overrides` can't reach it. It's patched where the route looks it up:

```python
monkeypatch.setattr(
    "app.api.routes.quizzes.get_llm_provider",
    lambda: StubProvider("VERDICT: correct\nFEEDBACK: Good explanation."),
)
```

Two tests go further and assert a provider is *never constructed at all* — by patching in a function that raises if called. That pins a real promise the route's own comment makes: an MCQ-only submission must work with no LLM configured, and a blank free-text answer must not spend an API call on nothing.

```python
def fail_if_called():
    raise AssertionError("provider must not be constructed for mcq-only grading")
```

The suite was then confirmed genuinely offline by monkeypatching `socket.socket.connect` to raise and re-running: **31 passed with sockets blocked.** That satisfies M7.3's stated criterion ("confirm no test makes a real network call") by demonstration rather than by inspection.

### Ordering is tested against a hostile fixture
The quiz fixture seeds its MCQ choices **deliberately out of order** — the wrong answer at `order=2` inserted first, the right one at `order=1` second — so the test that asserts they come back `["Right answer", "Wrong answer"]` can only pass if `Choice.order`'s `order_by` is genuinely doing the sorting. Seeding them in the correct order would have made the assertion pass whether the ordering logic existed or not.

## The tests were validated by breaking the code

Passing tests prove nothing on their own — a test that asserts something always true passes forever and catches nothing. Each of the four properties above was verified by deliberately introducing the corresponding bug and confirming the suite went red:

| Mutation introduced | Result |
|---|---|
| Add `is_correct` to `ChoiceRead` (leak the answer key) | 1 failed |
| Unanswered question graded `False` instead of `None` | 2 failed |
| Construct the LLM provider eagerly instead of lazily | 2 failed |
| Remove `order_by="Choice.order"` from the relationship | 1 failed |

All four were caught, and each restore was confirmed byte-identical to the original by md5 before moving on.

## Two real problems found along the way

**1. The Phase 5 code had never been formatted or linted.** Running `black --check` across the backend showed 46 files clean and exactly 4 dirty — and the 4 were precisely the new quiz files. `ruff` agreed, flagging three `E501` line-length violations and one unsorted import block in `quizzes.py` and `grading.py`. So the feature had been written, hand-verified, and marked done without ever going through the project's own toolchain. Fixed by running both. Worth noting that the *only* reason this was detectable was the contrast: if the whole repo had been unformatted, nothing would have stood out.

**2. Black introduced a redundant construct while fixing a line-length error.** A long f-string was manually split across two lines to get under 88 characters; black then rejoined them onto one line, leaving `f"..." f"..."` — an implicit string concatenation of two adjacent f-strings that does nothing. Harmless, but noise. Collapsed back to a single f-string. A small reminder that autoformatter output still deserves a read rather than a blind commit.

## Why these tests and not more
The route layer is where the interesting logic lives, so that's where the tests are. Deliberately **not** tested: Pydantic's own serialization, SQLAlchemy's own relationship loading, and FastAPI's own routing — all of which are somebody else's well-tested code, and testing them here would produce tests that fail on library upgrades without indicating any real bug.

`test_grading.py` tests `grade_open_ended()` directly rather than only through the route because its regex parsing has real edge cases — a case-insensitive verdict, multi-line feedback, and a model that ignores the requested format entirely (which must degrade to "incorrect, with the raw reply as feedback" rather than raising and 500ing the whole submission).

## Terms worth knowing
- **Mutation testing:** deliberately introducing a bug to confirm the test suite detects it. The only real evidence that a passing test is load-bearing rather than decorative.
- **`monkeypatch`:** pytest's fixture for temporarily replacing an attribute, automatically undone at test end. Patch where the name is *looked up*, not where it's defined — patching `app.services.llm.factory.get_llm_provider` would have missed, because the route imported the name into its own module namespace.
- **Test double / stub:** a stand-in returning canned data instead of doing real work. Here, a fixed grader reply so an assertion doesn't depend on what a live model happens to say.
