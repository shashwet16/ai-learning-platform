# M7.1 — Backend Test Harness

## One-line summary
A fixture-backed test database that gives every test a fresh, empty schema and an HTTP client wired to it — running entirely in-memory, with no Postgres, no network, and no state leaking between tests.

## The problem
Up to this point the backend had 13 tests, and every one of them was a pure unit test — password hashing, JWT encoding/decoding, the LLM provider factory. Not one of them ever touched a database or made an HTTP request. That meant the entire API surface (auth, courses, exercises, chat, quizzes) had **zero** automated coverage: every route had only ever been verified by hand with `curl` or in a browser, once, at the moment it was written.

The blocker was that testing a route means giving it a database. Doing that naively creates two problems: tests that talk to the real development Postgres will destroy real seed data, and tests that share one database will leak state into each other — test B passes only because test A happened to run first and left a row behind.

## What we built
`backend/app/tests/conftest.py`, providing three fixtures:

- **`db`** — a fresh, empty in-memory SQLite database per test
- **`client`** — a FastAPI `TestClient` whose `get_db` dependency is overridden to hand out that same session
- **`lesson`** — a committed `Lesson`, with the `Course` → `Module` → `Lesson` foreign-key chain it requires

Plus `test_health.py`, M7.1's own stated acceptance criterion.

## How it works

```python
engine = create_engine(
    "sqlite://",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,
)
Base.metadata.create_all(engine)
```

Three decisions are doing real work here, and two of them were made *against* the obvious choice.

### 1. SQLite, despite a Postgres-specific schema

The models use `sqlalchemy.dialects.postgresql.UUID` for every primary key, and `Question.question_type` is a **native Postgres enum**. Both look like they'd hard-require a live Postgres to run against.

They don't, as of SQLAlchemy 2.0: the dialect-specific `postgresql.UUID` now subclasses the backend-agnostic `Uuid` type and renders as `CHAR(32)` on SQLite, and the generic `Enum` renders as `VARCHAR` plus a `CHECK` constraint. This was **verified empirically before building anything on top of it**, not assumed from reading release notes:

```
$ python -c "Base.metadata.create_all(create_engine('sqlite://'))"
SQLite create_all: OK
sqlalchemy 2.0.36
```

That check is the reason the harness is a few lines of fixture instead of a docker-compose Postgres and a CI service container.

### 2. Rejecting SQLAlchemy's own recommended test recipe

The SQLAlchemy docs recommend a specific pattern for test suites, "Joining a Session into an External Transaction": open a connection, begin a real transaction, bind the session with `join_transaction_mode="create_savepoint"`, and roll the outer transaction back in teardown. It's elegant — the schema is built once for the whole suite, and each test's changes vanish on rollback, so it's fast.

**It does not work on SQLite**, and the trap is that it fails *silently* rather than erroring. From SQLAlchemy's own SQLite dialect documentation:

> "Incorrect behavior for SAVEPOINT — as the SAVEPOINT statement does not imply a BEGIN, a new SAVEPOINT emitted before a BEGIN will function on its own but fails to participate in the enclosing transaction"

pysqlite's legacy transaction mode is on by default, so `join_transaction_mode="create_savepoint"` produces savepoints that aren't inside the outer transaction. The rollback then doesn't undo them. You'd get a suite that appears to work and leaks state between tests — the exact bug the pattern exists to prevent, reintroduced by the fix for it.

There is a documented workaround (event listeners that null out `isolation_level` and emit `BEGIN` manually, or `connect_args={"autocommit": False}` on Python 3.12+). We deliberately **didn't** take it. A throwaway engine plus `create_all` per test sidesteps the whole class of problem with no event-listener machinery to misconfigure, and the cost — rebuilding ~10 tables in memory per test — is genuinely nothing at this suite size. The full 31-test suite runs in ~2.1s.

This is a case where the "best practice" recipe is correct for the database it assumes and actively harmful for the one actually in use. The reasoning is recorded in the fixture's docstring so the next person doesn't "upgrade" it to the savepoint version.

### 3. `StaticPool` + `check_same_thread=False`

An in-memory SQLite database exists only inside its own connection — open a second connection and you get a second, empty database. `TestClient` runs the app in a separate thread from the test function, so without `StaticPool` (which holds exactly one connection and hands the same one to everybody) the fixture would seed data into a database the route never sees. `check_same_thread=False` is what lets pysqlite hand that single connection across the thread boundary at all.

```python
fastapi_app.dependency_overrides[get_db] = lambda: db
try:
    yield TestClient(fastapi_app)
finally:
    fastapi_app.dependency_overrides.clear()
```

The `clear()` is in a `finally` for a specific reason: `app` is a module-level singleton imported by every test module. An override left behind by a failing test would silently apply to the rest of the suite.

## Verification

`test_health.py` covers M7.1's stated acceptance criterion, and does it in two steps rather than one. `GET /health` proves routing and the client fixture work. `GET /health/db` proves more — it runs `SELECT 1` through `Depends(get_db)`, so it passes **only** if the override genuinely reached the route and injected the fixture's SQLite session. Without the override it would hit the configured Postgres or fail outright.

The suite was also confirmed to be genuinely offline, rather than assumed to be, by monkeypatching `socket.socket.connect` to raise and re-running:

```
31 passed   (sockets blocked)
```

## Why not the alternatives

- **A real Postgres test database (docker-compose / CI service):** highest fidelity — it would catch native-enum rejection and other Postgres-only behavior that SQLite's `CHECK` constraint only approximates. Rejected for now because it makes `pytest` require a running service, which is a real ongoing cost for a solo project. This is an honest, known gap, recorded below.
- **Mocking the database layer entirely:** would test the routes against a fiction. The bugs worth catching here — a missing `selectinload`, a wrong `order_by`, a schema that leaks a field — only appear when real SQL runs against a real schema.
- **One shared database with per-test cleanup:** cleanup code is itself untested code, and it fails open. A test that forgets to clean up passes, and breaks a different test later.

## Known limitation
Tests run on SQLite, so genuinely Postgres-only behavior isn't covered: the native `question_type` enum is a `VARCHAR` + `CHECK` here, `ondelete="CASCADE"` isn't enforced unless SQLite's foreign-key pragma is on, and Postgres-specific SQL would pass locally and fail in production. The mitigation is that the schema is still generated from the same SQLAlchemy models, so structural drift is caught even where dialect behavior isn't.

## Terms worth knowing
- **Fixture:** a pytest function that builds a dependency for a test and tears it down afterward, requested by naming it as a test argument. Scope controls reuse — these are function-scoped, so every test gets its own.
- **Dependency override:** FastAPI's built-in hook for swapping out a `Depends(...)` provider at test time, without the application code knowing it's under test.
- **SAVEPOINT:** a named marker inside a transaction that can be rolled back to without discarding the whole transaction — what nested-transaction test isolation is built on, and what pysqlite's default mode gets wrong.
- **Connection pool:** the set of live DB connections an engine reuses. `StaticPool` is the degenerate case — exactly one connection, forever — which is normally undesirable and is exactly right for an in-memory test DB.

## If asked in an interview
> "The interesting part of the test harness was rejecting SQLAlchemy's own documented recipe for it. The standard pattern is to bind the session to an external transaction with `join_transaction_mode='create_savepoint'` and roll back per test. But SQLAlchemy's SQLite docs say pysqlite emits SAVEPOINT without an enclosing BEGIN in its default transaction mode, so those savepoints don't participate in the outer transaction — the rollback silently doesn't roll anything back. You'd get a suite that looks isolated and leaks state, which is worse than no isolation because you'd trust it. I used a throwaway in-memory engine per test instead; at this suite size the rebuild cost is nothing, and there's no event-listener machinery to misconfigure later. I also checked the assumption underneath all of it empirically — the models use Postgres-specific UUID columns, which I expected would force a real Postgres, but in SQLAlchemy 2.0 that type subclasses the generic `Uuid` and renders as CHAR(32) on SQLite, so I verified `create_all` actually succeeded before building anything on top of it."
