# M0.5 — Environment Config Management

## One-line summary
Centralized, typed, fail-fast configuration on both sides instead of `os.environ.get(...)` scattered through the codebase.

## The problem
Every real app needs environment-specific values — a database URL, a JWT signing secret, an API key — that must never be hardcoded (especially secrets) and must differ between a developer's laptop, staging, and production. The naive approach, `os.environ.get("DATABASE_URL")` called wherever it's needed, has two problems: (1) a typo'd variable name fails silently (`os.environ.get` returns `None` instead of erroring), and (2) there's no single place to see every config value the app depends on.

## What we built
- **Backend**: `backend/app/core/config.py` — a Pydantic `Settings` class, instantiated once as `settings`
- **Frontend**: `frontend/src/config.ts` — reads `import.meta.env` (Vite's env-var mechanism)
- `backend/.env.example` and `frontend/.env.example` — checked into Git as documentation of every variable the app needs; the real `.env` files are git-ignored and never committed

## How it works — backend
```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    environment: Literal["development", "staging", "production"]
    database_url: str
    jwt_secret: str
    jwt_expire_minutes: int = 30
    mistral_api_key: str | None = None
    ...

settings = Settings()
```
This is **Pydantic Settings** — the same validation library used for API request/response schemas (`schemas/*.py`), applied to environment variables instead. Fields with no default (`database_url: str`, `jwt_secret: str`) are *required*: if the corresponding env var is missing, `Settings()` raises a validation error immediately at import time — the app refuses to even start, rather than starting broken and failing mysteriously on the first request that needs the database. Fields with a default (`jwt_expire_minutes: int = 30`) are optional.

`environment: Literal["development", "staging", "production"]` is a deliberate design choice: there's no default. A deployment must *explicitly* declare which environment it's running as — no silent fallback that could let a production deploy accidentally behave like dev.

## How it works — frontend
```typescript
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL

if (!apiBaseUrl) {
  throw new Error('Missing required env var VITE_API_BASE_URL. ...')
}

export const config = { apiBaseUrl } as const
```
Same fail-fast idea, simpler mechanism (no schema library on the frontend side — one variable doesn't need one). Vite only exposes env vars prefixed `VITE_` to browser code — a deliberate security boundary, since anything without that prefix (e.g. a server-side secret accidentally put in a `.env` file) is *not* bundled into the JavaScript shipped to the browser.

## Why this over `os.environ` calls scattered everywhere
- **Single source of truth**: every config value the app uses is declared in one file, so onboarding a new value means adding one line, not finding a `.env.example` file and hoping every call site is consistent.
- **Type safety**: `settings.jwt_expire_minutes` is a real `int`, not a string that happens to look like a number — no repeated `int(os.environ["JWT_EXPIRE_MINUTES"])` casting at every call site.
- **Fail fast, not fail silent**: a missing required var crashes at startup with a clear error, not three requests later with a confusing `NoneType has no attribute` deep in unrelated code.

## Terms worth knowing
- **Fail fast**: surfacing an error as early as possible (here: at process startup) rather than letting a bad state propagate and fail later in a harder-to-diagnose way.
- **`.env` file**: a local file of `KEY=value` lines, loaded into environment variables for local development. Always git-ignored — it's where real secrets live on a developer's machine.
- **`.env.example`**: the *documented, secret-free* counterpart that *is* committed — shows what variables exist and roughly what shape they take, without any real values.

## If asked in an interview
> "Config is a single typed Pydantic `Settings` object on the backend, read once at startup — any required variable that's missing crashes the app immediately with a clear validation error, instead of the more common failure mode where a missing env var quietly returns `None` and blows up three requests later somewhere unrelated."
