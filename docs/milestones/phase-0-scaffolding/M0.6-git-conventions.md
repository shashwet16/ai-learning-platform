# M0.6 — Git Conventions & Initial Commit

## One-line summary
Locking in commit/branch conventions and `.gitignore` coverage before real feature work started.

## The problem
It's much cheaper to decide "what do we commit, what do we never commit, how do we write commit messages" once at the start than to clean up an inconsistent history later — especially the "never commit" part, since a secret committed once is compromised forever (present in Git history even after being deleted in a later commit) unless the entire history is rewritten.

## What we built
- `.gitignore` finalized to cover: Python artifacts (`__pycache__/`, `.venv/`, `.ruff_cache/`), Node artifacts (`node_modules/`, `dist/`), secrets (`.env` and variants — with an explicit `!.env.example` exception so the documented, secret-free template *is* tracked), and editor/OS junk (`.DS_Store`, `.idea/`)
- One deliberate, project-specific line: `ROADMAP.md` is git-ignored — kept as a local planning document, not published to the public GitHub remote (see the project's commit-workflow notes for why)
- The first real commit containing all of Phase 0's scaffolding

## Why explicit `.gitignore` categories (not one flat list)
Grouping by comment header (`# --- Secrets ---`, `# --- Python (backend) ---`, etc.) instead of one undifferentiated list makes it obvious *why* each entry exists when someone (including future-you) reads the file later — a bare `*.env` with no context looks arbitrary; under a `# --- Secrets ---` header its purpose is self-evident.

## A specific project decision worth knowing: ROADMAP.md is intentionally excluded
This file — the one describing every milestone, decision, and trade-off — is deliberately *not* pushed to the public GitHub repo. It's a local planning/journal document; the public repo shows the resulting code and (once you read this docs/ tree) the resulting explanations, without exposing every intermediate planning note. Documented as its own project-level fact — see the project's memory notes if you need the full reasoning again.

## Terms worth knowing
- **Git-ignored**: matched by a `.gitignore` pattern, so Git never tracks changes to that file/path — it can still exist on disk, it's just invisible to `git status`/`git add`/`git commit`.
- **A secret in history is compromised even after deletion**: if `.env` is ever committed once, deleting it in a later commit does *not* remove it from history — anyone with clone access can still `git log` back to the commit that added it. The only real fixes are rotating the secret or rewriting history (`git filter-repo`, force-push) — both painful. Prevention (a correct `.gitignore` from commit one) is far cheaper.

## If asked in an interview
> "The `.gitignore` was set up before any real code, split into commented sections — secrets, Python artifacts, Node artifacts — specifically so it's obvious *why* each pattern exists, not just that it does. Secrets in particular get this treatment because once a `.env` file is committed once, it's in history forever unless you rewrite it — much cheaper to never let it happen."
