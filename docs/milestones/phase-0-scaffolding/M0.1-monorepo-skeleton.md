# M0.1 — Monorepo Skeleton

## One-line summary
Set up the repo so the backend and frontend live side-by-side in one Git repository instead of two separate ones.

## The problem
Before writing any real code, a project needs a home. This app has two completely different runtimes — a Python API server and a JavaScript/TypeScript browser app — and they need to live somewhere. There are two common ways to organize that:

- **Polyrepo**: `ai-learning-platform-backend` and `ai-learning-platform-frontend` as two separate Git repositories.
- **Monorepo**: one repository, `backend/` and `frontend/` as top-level folders inside it.

This project chose the monorepo layout.

## What we built
- `backend/` — everything Python/FastAPI
- `frontend/` — everything React/Vite/TypeScript
- `docs/` — project documentation (this folder)
- root `.gitignore` — one shared ignore file covering both Python and Node artifacts
- `README.md` — top-level project description

## Why a monorepo (and not two repos)
- **One commit can span both sides.** A feature like "add an exercises API" (M3.10) touches a new backend endpoint *and* a new frontend page that calls it. In a monorepo that's one commit telling one coherent story. In a polyrepo it'd be two commits in two repos that have to be manually kept in sync.
- **Small team of one.** Polyrepos earn their keep when different teams own different repos with different release cadences. A solo/small project gets none of that benefit and pays the cost of juggling two clone/PR/CI setups.
- **Simpler local dev.** `cd backend && uvicorn ...` and `cd frontend && npm run dev` from one checkout, instead of managing two separate working copies that need to stay checked out to compatible commits.

The trade-off, honestly: a monorepo doesn't scale infinitely (Google/Meta-scale monorepos need custom tooling to stay fast). At this project's size that ceiling is nowhere close.

## Terms worth knowing
- **Monorepo**: "mono" (one) + "repo" (repository) — multiple logically-separate projects committed into a single Git repository, sharing one history.
- **`.gitignore`**: a file listing patterns Git should never track (build output, dependency folders, secrets). One shared file at the repo root covers both `backend/` and `frontend/` since Git doesn't care which subfolder a pattern matches in.

## If asked in an interview
> "I used a monorepo — one Git repo with `backend/` and `frontend/` as top-level folders — because most features cut across both sides: a new backend endpoint almost always ships with the frontend code that calls it. Keeping them in one repo means one commit and one PR tells the whole story of a feature, instead of coordinating two repos manually."
