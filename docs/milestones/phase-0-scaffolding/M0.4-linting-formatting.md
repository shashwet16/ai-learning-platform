# M0.4 — Linting & Formatting

## One-line summary
Automated code-style enforcement on both sides, so style is never a matter of opinion or manual review effort.

## The problem
Without automated tooling, code style drifts — inconsistent quotes, unused imports left behind, indentation differences — and reviewers waste time commenting on style instead of substance. The fix is to make a machine enforce it.

## What we built
- **Backend**: Ruff (linter) + Black (formatter), configured in `backend/pyproject.toml`
- **Frontend**: originally ESLint/Prettier per the roadmap; the actual `package.json` shows the project settled on **oxlint** (a Rust-based linter, much faster than ESLint) + Prettier

## How it works
```toml
[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]
```
Each letter code is a rule category: `E`/`F` are pycodestyle/pyflakes basics (unused imports, undefined names), `I` is import sorting, `UP` flags code that could use a newer, cleaner Python syntax, `B` (`flake8-bugbear`) catches likely-bug patterns — like passing a mutable default argument, which is a classic Python footgun.

One real tuning decision lives right there in the config:
```toml
[tool.ruff.lint.flake8-bugbear]
extend-immutable-calls = ["fastapi.Depends", "fastapi.Query"]
```
Bugbear normally flags `def f(x=some_call()):` as dangerous, because a mutable default is evaluated once at function-definition time and shared across every call — a classic source of subtle bugs. But FastAPI's dependency-injection system (`Depends(get_db)`, seen in nearly every route in this project) is *designed* to be called exactly that way — it's not a bug, it's the framework's API. This line tells the linter about that specific, deliberate exception instead of just suppressing the whole rule.

`Black` handles pure formatting (line length, quote style, spacing) — deterministically, with no configuration decisions to argue about, which is the whole point of an "opinionated formatter."

## Why lint + format as two separate tools (not one)
A **linter** finds problems (unused variable, likely bug) that require a human or the linter's `--fix` to resolve — some flags genuinely need judgment. A **formatter** only rearranges whitespace/quotes/line-breaks — always safe to auto-apply, no judgment needed. Keeping them separate means formatting can run on every save with zero risk, while linting stays a deliberate check.

## Terms worth knowing
- **Linter**: static analysis that flags code patterns that are likely bugs or bad style, without executing the code.
- **Formatter**: rewrites code into one canonical whitespace/style layout, with no judgment calls — the same input always produces the same output.
- **`pyproject.toml`**: the modern, unified config file for Python tooling — one file where Black, Ruff, and the package's own metadata (dependencies, etc.) all live, replacing the older pattern of a separate `.flake8`, `setup.cfg`, `MANIFEST.in`, etc.

## If asked in an interview
> "Ruff and Black on the backend, oxlint and Prettier on the frontend — linting catches likely bugs (unused imports, mutable default arguments), formatting is purely mechanical whitespace/style, kept as two separate tools since only one of those categories is safe to auto-fix blindly."
