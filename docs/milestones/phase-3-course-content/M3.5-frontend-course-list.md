# M3.5 — Frontend Course List Page

## One-line summary
`/courses` — a browsable catalog of course cards, plus (done in this same milestone, beyond its original scope) a full frontend design-system overhaul.

## The problem
`GET /courses` (M3.3) exists, but nothing in the browser calls it yet. Someone needs to fetch and render the list.

## What we built
`frontend/src/api/courses.ts` (typed API functions + response interfaces) and `frontend/src/pages/CoursesPage.tsx`.

## How it works
```typescript
export function CoursesPage() {
  const [courses, setCourses] = useState<CourseSummary[] | null>(null)
  const [error, setError] = useState<string | null>(null)

  useEffect(() => {
    listCourses().then(setCourses).catch((err) => {
      setError(err instanceof ApiError ? err.message : 'Failed to load courses.')
    })
  }, [])

  if (error) return <p className="form-error">{error}</p>
  if (courses === null) return <p>Loading…</p>
  return (/* render course cards */)
}
```
This establishes the loading/error/data three-state pattern reused by essentially every data-fetching page in the app since (`CourseDetailPage`, `LessonPage`, `ChatWindow`): `null` means "still loading," a set `error` string means "the fetch failed," and a non-null, non-error `courses` array means "render the real content." `courses === null` specifically (not falsy-checking, e.g. not `!courses`) matters because an empty array `[]` is a perfectly valid *successful* result (a catalog with zero courses) that should render an empty list, not a loading spinner forever.

`frontend/src/api/courses.ts` mirrors the backend's Pydantic schemas as TypeScript interfaces (`CourseSummary`, `CourseDetail`, `LessonDetail`) — this is the same discipline noted in M0.3: if the backend schema changes shape, every frontend call site referencing the old shape fails to *compile*, rather than silently receiving `undefined` for a renamed field at runtime.

## The out-of-scope work folded into this milestone: a full design-system pass
The roadmap's own progress notes flag that "a full frontend design-system overhaul (typography, color, layout) was also done during M3.5" — this is exactly where the project's [[frontend-design-quality]] standard (never generic "AI slop," must read as artistic/professional) actually got established in code, not just as an aspiration. Concretely, that shows up as the CSS custom properties (`var(--ink-soft)`, seen in `App.tsx`'s dashboard greeting) and consistent component class conventions (`kicker`, `btn btn-primary`, `btn btn-quiet`) reused across every page since — `LoginPage`, `RegisterPage`, `CourseDetailPage`, `ChatPage` all draw from the same small set of shared classes rather than each page inventing its own styling.

## Why this loading/error/data pattern (and not, say, a spinner library or global loading state)
Keeping loading/error state local to each page component (rather than a single global "is anything loading" flag) means one slow request never blocks or confuses the UI for unrelated parts of the page — each fetch's status is independently and explicitly visible in that component's own render logic.

## Terms worth knowing
- **CSS custom properties (CSS variables)**: `--ink-soft` style declarations, defined once and referenced (`var(--ink-soft)`) throughout a stylesheet — enables a consistent, centrally-adjustable design system instead of repeating literal color/spacing values everywhere.
- **Three-state data fetching**: explicitly modeling "loading," "error," and "loaded" as distinct states (rather than just a boolean "isLoading") is what allows an empty successful result to render correctly instead of being indistinguishable from "still loading."

## If asked in an interview
> "Every data-fetching page follows the same pattern: `null` state means loading, a set error string means failed, anything else means render real data — checking `=== null` specifically so a legitimately empty result doesn't get mistaken for 'still loading.' This milestone also happened to be where the whole frontend design system — shared CSS variables and button/typography conventions every later page reuses — got established, which was more work than the milestone's original scope but became the visual foundation for everything built after it."
