# M3.3 — Course List & Detail Endpoints

## One-line summary
`GET /courses` and `GET /courses/{id}` — the read API for browsing the catalog, with the detail endpoint returning a full nested module/lesson tree in a single request.

## The problem
The frontend catalog page needs a list of courses; the course detail page needs one course's full module/lesson structure so it can render a navigable table of contents — without either page making a cascade of separate requests (one for the course, one per module, one per lesson) just to build one screen.

## What we built
`backend/app/schemas/course.py` (`CourseSummary`, `CourseDetail`, `ModuleSummary`, `LessonSummary`) and `backend/app/api/routes/courses.py`:
```python
@router.get("", response_model=list[CourseSummary])
def list_courses(db: Session = Depends(get_db)) -> list[Course]:
    return list(db.scalars(select(Course).order_by(Course.title)).all())

@router.get("/{course_id}", response_model=CourseDetail)
def get_course(course_id: uuid.UUID, db: Session = Depends(get_db)) -> Course:
    course = db.execute(
        select(Course).where(Course.id == course_id)
        .options(selectinload(Course.modules).selectinload(Module.lessons))
    ).scalar_one_or_none()
    if course is None:
        raise AppError("Course not found", status_code=404, code="course_not_found")
    return course
```

## How it works
- **`CourseSummary` vs. `CourseDetail`**: the list endpoint returns the lightweight shape (title, description, no modules) — a catalog page just needs enough to render cards, not each course's entire content tree. `CourseDetail` extends `CourseSummary` with `modules: list[ModuleSummary]`, each of which nests `lessons: list[LessonSummary]` — three levels of nested Pydantic models mirroring the three-level ORM hierarchy from M3.1. Note `LessonSummary` only has `id`, `title`, `order` — not `body` — the full Markdown content is deliberately withheld from the course-detail response (see M3.4) since a table-of-contents view has no use for it and it could be a meaningfully larger payload for a content-heavy course.
- **`selectinload(Course.modules).selectinload(Module.lessons)`** is the single most important line here, addressing a classic ORM performance trap called the **N+1 query problem**: without it, accessing `course.modules` triggers one query, and then accessing `.lessons` on *each* module triggers a separate query per module — for a course with 5 modules, that's 1 + 5 = 6 queries instead of 1. `selectinload` tells SQLAlchemy to eagerly fetch modules and their lessons in a small, fixed number of additional `SELECT ... WHERE id IN (...)` queries up front, so the nested access after that is just reading already-loaded Python objects — no queries fired lazily one at a time as `response_model` serialization walks the tree.
- **No auth on these routes** — deliberately public, per a comment carried into M3.10's exercises route (`# Public, no Depends(get_current_user) — same as course/lesson reads`) — browsing course content doesn't require being logged in; only per-user actions (submissions, chat, progress) do.

## Why nested response schemas + eager loading (not N separate endpoints)
- **One request, one round trip** for the whole course detail screen — meaningfully faster over a real network than a waterfall of sequential requests the frontend would otherwise need to orchestrate.
- **Eager loading fixes what nesting would otherwise make worse**: returning a deeply nested response is exactly the shape most likely to accidentally trigger N+1 lazy-loading if you don't explicitly tell the ORM to batch-fetch ahead of time — this endpoint is a good, concrete example of *why* that matters, not just an abstract warning.

## Terms worth knowing
- **N+1 query problem**: a performance anti-pattern where fetching a list of N parent records, then lazily fetching each one's related child records inside a loop, produces 1 + N database round trips instead of a small constant number.
- **Eager loading**: fetching related data up front, in the same or a tightly-batched set of queries, rather than lazily on first access.
- **`selectinload` vs. `joinedload`**: two SQLAlchemy eager-loading strategies — `selectinload` issues a separate `SELECT ... IN (...)` per relationship level (what's used here), `joinedload` uses a single SQL `JOIN` instead. `selectinload` tends to scale better for one-to-many relationships with potentially many children, since a `JOIN` would duplicate parent row data once per child row.

## If asked in an interview
> "The course detail endpoint returns the full module/lesson tree in one response, using `selectinload` to eager-load both relationship levels up front — without that, serializing the nested response would trigger the classic N+1 problem: one query for modules, then one more query *per module* for its lessons. `selectinload` collapses that into a small fixed number of batched queries regardless of how many modules a course has."
