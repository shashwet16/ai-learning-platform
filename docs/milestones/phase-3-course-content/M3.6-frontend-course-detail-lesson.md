# M3.6 — Frontend Course Detail + Lesson Viewer

## One-line summary
Clicking a course shows its module/lesson tree; clicking a lesson renders real formatted Markdown with prev/next navigation — the first milestone where lesson content actually becomes readable.

## The problem
`CourseDetailPage` needs to render the nested module/lesson structure from M3.3 as a navigable table of contents, and `LessonPage` needs to turn a raw Markdown string (M3.1's `Lesson.body`) into actual formatted HTML in the browser, plus wire up the prev/next links from M3.4.

## What we built
`frontend/src/pages/CourseDetailPage.tsx` and `frontend/src/pages/LessonPage.tsx`, plus `react-markdown` added as a dependency.

## How it works
`CourseDetailPage` is a straightforward nested render — `course.modules.map(...)` → `module.lessons.map(...)` → a `<Link to={`/lessons/${lesson.id}`}>` per lesson — directly mirroring the nested `CourseDetail`/`ModuleSummary`/`LessonSummary` shape from M3.3.

`LessonPage` is more involved:
```tsx
useEffect(() => {
  if (!lessonId) return
  setLesson(null)   // reset before fetching — see below
  setError(null)
  getLesson(lessonId).then(setLesson).catch(...)
}, [lessonId])

return (
  <div className="lesson-page">
    <article className="prose">
      <Markdown>{lesson.body}</Markdown>
    </article>
    <nav className="lesson-nav">
      {lesson.prev_lesson_id ? <Link to={...}>← Previous</Link> : <span />}
      {lesson.next_lesson_id && <Link to={...}>Next lesson →</Link>}
    </nav>
  </div>
)
```
Two details worth understanding:
1. **`setLesson(null)` before fetching, not just on error** — with a comment explaining exactly why: "otherwise clicking 'next lesson' would keep showing the previous lesson's content while the new one is still loading, since `lesson` would still hold the old value." Without this reset, navigating from lesson A to lesson B via the "Next" link changes the URL and re-triggers the `useEffect` (since `lessonId` changed), but until the new fetch resolves, the *old* lesson's content would remain on screen, which looks like the click did nothing until it suddenly jumps — this reset makes the transition show a clean loading state instead.
2. **`<Markdown>{lesson.body}</Markdown>`** — `react-markdown` parses the Markdown string and renders real DOM elements (`<h1>`, `<strong>`, `<ul><li>`, `<pre><code>`) rather than dumping raw text with literal `#`/`**` characters visible. This is the same library and pattern reused later by `ChatWindow` for assistant replies (M3.8) — established here first for lesson content.

This is also the extension point M3.7 (Mermaid diagrams) and M3.9 (the code playground) later build on: `LessonPage`'s `markdownComponents` prop overrides how `react-markdown` renders specific elements (like fenced code blocks), which is what lets a ` ```mermaid ` or ` ```python-playground ` fence route to a completely different, interactive component instead of a plain `<pre><code>` block — that override mechanism didn't exist yet in this milestone, but the base `<Markdown>` render this milestone introduced is exactly what those later milestones extend.

## Why `react-markdown` (and not `dangerouslySetInnerHTML` with a separate Markdown-to-HTML step)
`react-markdown` parses Markdown into a syntax tree and renders it through actual React elements — critically, it does **not** use `dangerouslySetInnerHTML` and doesn't execute arbitrary embedded HTML by default, which matters directly for M8.2's later security concern (sanitizing user/lesson content against XSS). A naive "convert Markdown to an HTML string, then inject it" approach would require a separate sanitization step to be safe against embedded `<script>` tags; `react-markdown`'s component-based rendering sidesteps that risk by construction.

## Terms worth knowing
- **Markdown**: a lightweight plain-text formatting syntax (`# heading`, `**bold**`, `` `code` ``) designed to be readable even unrendered, and cheaply convertible to HTML.
- **XSS (Cross-Site Scripting)**: injecting malicious script into content that later gets rendered as trusted HTML in another user's browser — a risk specifically tied to *how* you render user-influenced content, which is why the rendering library choice here isn't incidental.
- **`dangerouslySetInnerHTML`**: React's escape hatch for injecting a raw HTML string directly into the DOM — named deliberately scary because it bypasses React's normal escaping and is a common XSS vector if the HTML source isn't fully trusted/sanitized.

## If asked in an interview
> "Lesson content renders through `react-markdown`, which builds real React elements from parsed Markdown rather than injecting raw HTML — no `dangerouslySetInnerHTML` anywhere, which matters for XSS safety since lesson bodies are just text in the database, not something explicitly sanitized on the way in. One easy-to-miss detail in the lesson page itself: navigating to a new lesson has to explicitly reset the displayed lesson to `null` before fetching, or clicking 'next' would keep the old lesson's content on screen until the new one finishes loading, which looks broken even though the fetch is working correctly."
