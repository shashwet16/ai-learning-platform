# M3.4 — Lesson Detail Endpoint

## One-line summary
`GET /lessons/{id}` — serves a lesson's full content plus prev/next navigation that correctly flows across module boundaries, not just within one module.

## The problem
Reading one lesson needs its full body (unlike the course-detail view, which deliberately omits it — M3.3), and needs to know what to read next — including the case where "next" means "the first lesson of the *next* module," not a dead end at the last lesson of the current one.

## What we built
```python
@lessons_router.get("/{lesson_id}", response_model=LessonDetail)
def get_lesson(lesson_id: uuid.UUID, db: Session = Depends(get_db)) -> LessonDetail:
    lesson = db.get(Lesson, lesson_id)
    if lesson is None:
        raise AppError("Lesson not found", status_code=404, code="lesson_not_found")
    module = db.get(Module, lesson.module_id)

    course_lessons = list(db.scalars(
        select(Lesson).join(Module, Lesson.module_id == Module.id)
        .where(Module.course_id == module.course_id)
        .order_by(Module.order, Lesson.order)
    ).all())
    index = next(i for i, entry in enumerate(course_lessons) if entry.id == lesson.id)
    prev_lesson_id = course_lessons[index - 1].id if index > 0 else None
    next_lesson_id = course_lessons[index + 1].id if index < len(course_lessons) - 1 else None
    return LessonDetail(..., prev_lesson_id=prev_lesson_id, next_lesson_id=next_lesson_id)
```

## How it works
The key design decision, called out directly in the code's own comment:
> Prev/next must flow across module boundaries — a reader finishing the last lesson of one module should continue into the first lesson of the next module, not hit a dead end just because the module changed.

The naive approach — "find this lesson's siblings within its own module" — would break exactly at every module boundary, producing a jarring "no next lesson" at the end of every module except the last one in the course. Instead, the query **joins `Lesson` to `Module`** and orders by `(Module.order, Lesson.order)` — this flattens the entire course's lessons, across every module, into one single linear sequence, matching the actual reading order a learner experiences top-to-bottom through a course. Finding `lesson`'s position in that flattened list (`next(i for i, entry in enumerate(...) if entry.id == lesson.id)`) and taking `index - 1` / `index + 1` gives correct prev/next regardless of whether the neighbor happens to be in the same module or not.

`prev_lesson_id`/`next_lesson_id` are `None` at the very start/end of the course — the frontend (M3.6) uses that to decide whether to render a "Previous"/"Next" button at all, rather than a disabled or broken link.

Notice this endpoint constructs a `LessonDetail` directly rather than returning the ORM `Lesson` object with `response_model` doing the filtering (contrast with `get_course` in M3.3) — because `prev_lesson_id`/`next_lesson_id` aren't real columns on the `Lesson` model at all; they're computed per-request, so they have to be assembled into the response schema explicitly rather than mapped automatically via `from_attributes`.

## Why compute this per-request (and not store `next_lesson_id` on the Lesson row)
Storing a denormalized `next_lesson_id` column on `Lesson` would need to be kept in sync every time a lesson is added, removed, or reordered anywhere in the course — an easy source of stale/incorrect data (a classic denormalization trade-off). Computing it fresh on every read guarantees it's always consistent with the actual current `order` values, at the cost of one extra query per lesson view — a completely acceptable trade for a read pattern that isn't remotely hot enough to need that optimization.

## Terms worth knowing
- **Denormalization**: deliberately storing derived/redundant data (like a precomputed "next" pointer) to speed up reads, at the cost of needing to keep it in sync on every write that could invalidate it.
- **Flattening a hierarchy for traversal**: converting a nested structure (modules containing lessons) into one flat, ordered sequence when the actual use case (sequential reading) doesn't care about the hierarchy boundary.

## If asked in an interview
> "The tricky part of this endpoint isn't fetching the lesson — it's computing prev/next correctly across module boundaries. The query joins Lesson to Module and orders by `(module order, lesson order)` to flatten the whole course into one linear reading sequence, so finishing the last lesson of a module correctly continues into the next module's first lesson instead of hitting a false dead end. It's computed fresh per request rather than stored, so reordering content anywhere in the course can never leave a stale pointer behind."
