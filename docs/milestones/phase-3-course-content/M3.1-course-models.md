# M3.1 — Course/Module/Lesson Models

## One-line summary
The three-level content hierarchy — `Course → Module → Lesson` — that everything about learning content builds on.

## The problem
Course content needs structure: a course has multiple modules (topic groupings), each module has multiple lessons (individual reading units), and both need a defined, stable order — a "chapter 3 before chapter 4" guarantee.

## What we built
`backend/app/models/course.py`:
```python
class Course(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "courses"
    title: Mapped[str] = mapped_column()
    description: Mapped[str] = mapped_column(Text)
    modules: Mapped[list["Module"]] = relationship(
        back_populates="course", cascade="all, delete-orphan", order_by="Module.order")

class Module(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "modules"
    course_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("courses.id", ondelete="CASCADE"))
    title: Mapped[str] = mapped_column()
    order: Mapped[int] = mapped_column()
    course: Mapped["Course"] = relationship(back_populates="modules")
    lessons: Mapped[list["Lesson"]] = relationship(
        back_populates="module", cascade="all, delete-orphan", order_by="Lesson.order")

class Lesson(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "lessons"
    module_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("modules.id", ondelete="CASCADE"))
    title: Mapped[str] = mapped_column()
    body: Mapped[str] = mapped_column(Text)
    order: Mapped[int] = mapped_column()
    module: Mapped["Module"] = relationship(back_populates="lessons")
```

## How it works
- **A three-level tree via two foreign keys**: `Module.course_id` links up to `Course`, `Lesson.module_id` links up to `Module` — a lesson has no direct `course_id`; its course is only reachable by going through its module (this is exactly why M3.4's lesson endpoint has to join through `Module` to find sibling lessons across the whole course — see that doc).
- **`order: Mapped[int]`** on both `Module` and `Lesson` — an explicit integer column, not relying on insertion order or `created_at`, because content order needs to be independently *editable* (reordering lessons shouldn't require re-inserting rows or touching timestamps).
- **`relationship(..., order_by=...)`** — SQLAlchemy relationships are configured to *always* return their children pre-sorted by that `order` column. Any code that does `course.modules` or `module.lessons` gets them back in the correct display order automatically — no route needs to remember to sort.
- **`cascade="all, delete-orphan"`** on both parent relationships — deleting a `Course` deletes its `Module`s, which deletes their `Lesson`s, all the way down. Combined with `ondelete="CASCADE"` on the FK columns themselves, this cleanup happens correctly whether a delete happens through the ORM or via raw SQL.
- **`body: Mapped[str] = mapped_column(Text)`** — a lesson's content is stored as a single Markdown string (see M3.6 for how the frontend renders it, and M3.7 for the Mermaid-diagram extension of that same field). No separate rich-content table or block-based structure — the whole lesson body is one text blob, which is simple to author and simple to render, at the cost of no fine-grained structure (can't easily query "which lessons mention X concept in paragraph 2," for instance — not a need this project currently has).

## Why a fixed 3-level hierarchy (Course → Module → Lesson), not something more generic
A generic, arbitrarily-nestable tree (a single `ContentNode` table with a `parent_id` pointing to itself) is more flexible but meaningfully harder to reason about and query — "get me this course's modules" is `WHERE course_id = ?` on a fixed schema, versus a recursive query on a self-referential one. This project's actual content shape (courses made of a handful of modules, each with a handful of lessons) doesn't need arbitrary depth, so the simpler, fixed schema was the right trade-off.

## Terms worth knowing
- **One-to-many relationship**: one `Course` has many `Module`s; enforced via the foreign key living on the "many" side (`Module.course_id`), not the "one" side.
- **`back_populates`**: tells SQLAlchemy that two relationship declarations (`Course.modules` and `Module.course`) are two sides of the same association, so setting one from Python code keeps the other consistent in memory.
- **Cascade delete**: automatically deleting dependent rows when their parent is deleted — configurable at both the ORM level (`cascade=`) and the database level (`ondelete=`).

## If asked in an interview
> "Content is a fixed three-level hierarchy — Course, Module, Lesson — each level linked by a foreign key to its parent, with an explicit `order` integer column so display order is independently editable rather than tied to insertion order. Every relationship is configured with `order_by` so fetching a course's modules, or a module's lessons, always comes back correctly sorted without any route having to remember to sort it."
