# M3.2 — Seed Script

## One-line summary
A script that populates the database with a real course ("Intro to AI Engineering") so every later milestone has actual content to build and test against.

## The problem
An empty database makes frontend and backend development much harder — every page would show empty states, every "does pagination/ordering/nesting work" question would need manually inserted throwaway rows first. A seed script gives a one-command, reproducible way to get realistic data.

## What we built
`backend/app/scripts/seed_courses.py` — a standalone script (not an API route) that uses the app's own models and `SessionLocal` to insert one course, several modules, and multiple lessons with real Markdown bodies.

## How it works
The script imports the same `SessionLocal` and model classes (`Course`, `Module`, `Lesson`) that the running application uses — it's not a separate SQL file or fixture format, it's ordinary Python using the ORM, which means the data it creates is guaranteed to be structurally valid (foreign keys, required fields) the same way any other write to the database would be. Run directly (`python -m app.scripts.seed_courses` or similar), it opens a session, builds the object graph (a `Course` with `Module`s, each with `Lesson`s), and commits.

Content-wise, this seed script is also the origin of a real project constraint stated explicitly in the roadmap: every lesson's content is **original writing**, never scraped or copied from GeeksforGeeks, LeetCode, or similar sites, precisely because republishing their copyrighted material would be real legal exposure — informed by generally-known topic-progression research (e.g. public "AI engineer roadmap" lists), never by copying specific explanations.

## Why a script (and not a hand-written SQL fixture, or a database backup/restore)
- **Reuses real application code**: the script can't create structurally invalid data (a `Module` with no `course_id`, say) because it's going through the same SQLAlchemy models and constraints the app itself enforces — a hand-written SQL `INSERT` fixture could accidentally violate an assumption the ORM layer relies on.
- **Version-controlled and diffable**: the script lives in Git; changing seed content is a reviewable code diff, unlike a binary database dump.
- **Idempotent-ish and rerunnable on a fresh database**: any developer (or CI environment, per M7.1) can get identical realistic data with one command, without needing access to a shared "reference" database.

## Terms worth knowing
- **Seed data / seeding**: populating a database with a known, realistic (or synthetic) dataset for development or testing, as opposed to production data.
- **Fixture**: a broader term for a fixed, known piece of test/dev data — a seed script is one way to produce fixtures; hard-coded JSON/SQL files are another.

## If asked in an interview
> "The seed script uses the app's own SQLAlchemy models rather than raw SQL, so seeded data automatically respects every constraint the application itself enforces — it's not possible for the script to create a structurally invalid course tree. All the actual lesson content is original writing, deliberately never copied from sites like LeetCode or GeeksforGeeks, since republishing their material would be a real copyright problem, not just a style preference."
