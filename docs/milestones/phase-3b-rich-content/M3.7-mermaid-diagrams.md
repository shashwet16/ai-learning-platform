# M3.7 — Diagram Rendering in Lessons (Mermaid)

## One-line summary
A ` ```mermaid ` fence in lesson content now renders as a real SVG diagram — not diagram-shaped text — and does so without taxing every page that doesn't need it.

## The problem
Lessons explaining, say, an agent's control loop or a RAG pipeline are much clearer with an actual diagram than a wall of prose. This milestone came directly from user feedback that lessons were "way too basic" (see Phase 3B's own intro note in the roadmap) — the request specifically named visual diagrams as one of three concrete asks (diagrams, runnable code, deeper curriculum).

## What we built
`frontend/src/components/MermaidDiagram.tsx`, plus a `markdownComponents` override in `LessonPage.tsx` that routes a ` ```mermaid ` fenced code block to this component instead of a plain `<pre><code>`.

## How it works
Mermaid.js is a library that turns a small text-based diagram description (flowcharts, sequence diagrams, etc. — a syntax, not free-form drawing) into an SVG. The component:
```typescript
export function MermaidDiagram({ chart }: MermaidDiagramProps) {
  const containerRef = useRef<HTMLDivElement>(null)
  useEffect(() => {
    import('mermaid').then(({ default: mermaid }) => {
      initializeMermaidOnce(mermaid)
      return mermaid.render(`mermaid-${diagramId}`, chart)
    }).then((result) => {
      if (containerRef.current) containerRef.current.innerHTML = result.svg
    })
  }, [chart, diagramId])
  return <div className="mermaid-diagram" ref={containerRef} />
}
```
`LessonPage.tsx`'s custom `pre` renderer inspects the fenced block's language class:
```tsx
if (className === 'language-mermaid') {
  return <MermaidDiagram chart={String(fenceContent ?? '')} />
}
```
So a lesson author just writes a normal ` ```mermaid ` fence in the Markdown body — `react-markdown`'s component-override mechanism (introduced conceptually in M3.6, put to real use for the first time here) intercepts that specific fence and swaps in a live, rendered diagram instead of a code block.

`initializeMermaidOnce` also reads `window.matchMedia('(prefers-color-scheme: dark)')` and sets Mermaid's theme accordingly — the diagram matches the user's OS-level dark/light preference, rather than always rendering in one fixed theme regardless of the surrounding page. `securityLevel: 'strict'` sanitizes any HTML/script that might appear inside a diagram's labels — defense-in-depth against XSS even though diagram source currently only comes from this project's own seed content (see M3.6's XSS discussion — the same underlying concern, applied here to a different rendering path).

## A real bug caught and fixed: bundle bloat from a static import
The roadmap's progress notes are explicit about this:
> static import was adding ~110KB gzip to the main chunk loaded on every page, switched to a dynamic `import('mermaid')` inside the component so it's only fetched when a lesson with a diagram is actually viewed.

If `MermaidDiagram.tsx` had written `import mermaid from 'mermaid'` at the top of the file (a **static import**), Vite's bundler (M0.3) would include Mermaid's entire library in the app's *main* JavaScript chunk — the file downloaded on every single page load, including the login page, the chat page, and any lesson with no diagram at all. A **dynamic import**, `import('mermaid')` called *inside* the component's `useEffect`, tells the bundler to split Mermaid into its own separate chunk that's only fetched over the network the moment this component actually mounts — i.e., only when a lesson containing a real diagram is being viewed. This was caught by actually measuring bundle size (`npm run build` output), not assumed — the same measurement discipline shows up again in M3.9's much larger Pyodide/CodeMirror bundle-size fix.

## Why Mermaid (and not hand-drawn SVG, or an image per diagram)
- **Text-based, version-controllable diagrams**: a diagram lives as plain text inside the lesson's Markdown body — reviewable in a diff, editable without a graphics tool, consistent with how the rest of the lesson content is authored.
- **Theme-aware automatically**: a static image (PNG/SVG exported once) would need two versions to support dark mode; Mermaid renders fresh each time with the correct theme already applied.
- **Renders in the actual page's context**: no separate image asset to host, size, or keep in sync with the surrounding lesson text if it needs editing later.

## Terms worth knowing
- **Static import vs. dynamic import**: a static `import x from 'y'` at a file's top level is resolved and bundled at build time, unconditionally; a dynamic `import('y')` (a function call, usable anywhere in code, including conditionally) is resolved at runtime and lets a bundler split that dependency into a separate file fetched on demand.
- **Code splitting**: a bundler's ability to break an application's JavaScript into multiple separate files, so a browser only downloads the code actually needed for the current page/interaction, rather than the entire app upfront.
- **Gzip size vs. raw size**: browsers download compressed assets; "gzip size" (what's actually transferred) is the number that matters for load time, distinct from the uncompressed "raw size" of the source.
