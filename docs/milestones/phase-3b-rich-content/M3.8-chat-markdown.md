# M3.8 — Markdown Rendering in Chat Replies

## One-line summary
AI tutor replies now render as real formatted text — headers, bold, lists, code blocks — instead of showing literal `### ` and `**bold**` syntax in the chat thread.

## The problem
An LLM asked to "explain X with a bulleted list" naturally replies using Markdown syntax, because that's the format it's trained to produce for structured text. Before this milestone, `ChatWindow` rendered every message as plain text — so a nicely-structured reply from the model showed up as raw, ugly `### Heading\n- item one\n- item two` instead of an actual heading and bullet list.

## What we built
A one-line-of-reasoning change to `frontend/src/components/ChatWindow.tsx`: assistant messages render through `react-markdown` (the same library and rendering approach established in M3.6 for lesson bodies); the user's own messages stay plain text.

## How it works
```tsx
{message.role === 'assistant' ? (
  // Only assistant replies go through Markdown — the model is
  // prompted/expected to format with headers, lists, and code fences,
  // but the user's own input is a plain single-line text field, never
  // markdown-authored, so it stays as raw text.
  <div className="chat-markdown">
    <Markdown>{message.content}</Markdown>
  </div>
) : (
  message.content
)}
```
The asymmetry here is deliberate and worth understanding, not an oversight: only the `assistant` role's content goes through the Markdown parser. A user's message comes from a plain single-line `<input type="text">` (see `ChatWindow`'s form at the bottom) — nobody is typing `**bold**` syntax expecting it to render, and running user input through a Markdown renderer for no benefit would be pure wasted work (and, if the input format ever changed to something richer, a spot to reconsider for injection risk — see M3.6's XSS note, though `react-markdown`'s non-HTML-injecting rendering approach already contains that risk by construction either way).

A `.chat-markdown` CSS class scopes Markdown-specific styling (spacing for `<h1-h3>`, `<ul><li>`, `<pre><code>`) to just assistant bubbles, so it doesn't affect any other Markdown rendering elsewhere in the app (like `LessonPage`'s `.prose` styling).

## Why this over asking the LLM to "not use Markdown"
Prompting the model to avoid Markdown formatting entirely would fight against how these models are trained to produce well-structured answers, degrade response quality for legitimately list-shaped or code-heavy answers, and still be unreliable (a model can't be perfectly constrained by a system prompt alone). Rendering the Markdown correctly on the receiving end — work that had to happen exactly once, in one component — is both simpler and strictly better than trying to suppress a model behavior that's actually useful.

## A quirk hit during verification, deliberately not fixed here
Verifying this milestone surfaced (but didn't cause, and wasn't part of this milestone's job to fix) a pre-existing issue in `ChatPage.tsx`: the active conversation ID is stored under one un-namespaced `localStorage` key (`active_conversation_id`), with no per-user scoping. Switching accounts in the same browser without clearing storage means the new user's session tries to reuse the *previous* user's conversation ID, and `chat.py`'s ownership check (M4.5) correctly rejects it as "not found" rather than silently exposing the other user's chat — a real bug, but a narrow one (multi-account use in one browser), noted as a candidate follow-up rather than expanded scope creep into an unrelated milestone.

## Terms worth knowing
- **Role-based rendering**: treating `user` vs. `assistant` messages differently based on their known, trusted provenance — the assistant's role is known to produce Markdown by design; the user's role is known not to, so each gets the rendering treatment that actually fits its content.

## If asked in an interview
> "Only assistant messages go through the Markdown renderer — user input is a plain single-line field that's never markdown-authored, so rendering it through a parser would be pure wasted work with no benefit. This was a small change, but it closed a real gap: an LLM naturally produces Markdown-formatted answers when asked for structure, and without this, a nicely formatted response would show up as literal `###`/`**` syntax in the chat thread instead of an actual heading or bold text."
