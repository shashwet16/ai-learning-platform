# M3.9 — Interactive Python Code Playground (Ungraded)

## One-line summary
A lesson can embed a real, editable, runnable Python snippet — executed with actual CPython, entirely inside the learner's browser, with zero server-side code execution risk.

## The problem
Reading about Python is much weaker than running it. The obvious naive approach — send the learner's code to the backend, `exec()` or `subprocess` it, return the output — is a serious security problem: it means running arbitrary, untrusted, user-submitted code on your own server, which is one of the most dangerous things a backend can do (sandboxing that safely is a hard, well-known problem — container escapes, resource exhaustion, network access from inside the "sandbox," etc.). This milestone's entire design is built around avoiding that problem completely rather than trying to solve it.

## What we built
`frontend/src/components/CodePlayground.tsx` — a CodeMirror editor (with Python syntax highlighting) plus a "Run" button that loads **Pyodide** and executes the learner's code, wired into `LessonPage.tsx` via a ` ```python-playground ` fence (same override mechanism introduced in M3.7 for Mermaid).

## How it works
**Pyodide** is real CPython, compiled to WebAssembly, that runs directly in the browser's JavaScript engine — not a JavaScript reimplementation of a Python-like language, not a remote sandbox, an actual Python interpreter executing locally on the learner's own machine:
```typescript
function getPyodide(): Promise<PyodideAPI> {
  if (!pyodidePromise) {
    pyodidePromise = import('pyodide').then(({ loadPyodide }) =>
      loadPyodide({ indexURL: PYODIDE_INDEX_URL }))
  }
  return pyodidePromise
}
```
`pyodidePromise` is a **module-level singleton** — every `CodePlayground` instance on a page shares the same loading promise, so the (large — tens of MB) Pyodide runtime is fetched at most once, not once per playground on a page with several. It's also loaded **lazily on first "Run" click**, not on component mount — a learner reading a lesson who never clicks Run never downloads Pyodide at all.

```typescript
pyodide.setStdout({ batched: (text) => { buffer += buffer ? `\n${text}` : text } })
pyodide.setStderr({ batched: (text) => { buffer += buffer ? `\n${text}` : text } })
await pyodide.runPythonAsync(code)
setOutput(buffer || '(no output)')
```
Pyodide's stdout/stderr are redirected into a local buffer *per run* (re-set right before each execution, not once globally) so output shown is only ever from the most recent run — `runPythonAsync` actually executes the learner's edited code inside the WASM Python runtime.

## Two real bugs caught during build/verification (not written correctly the first time)

**1. Bundle bloat — same category of bug as M3.7's, bigger in scale.** Statically importing `@uiw/react-codemirror` + `@codemirror/lang-python` inflated the main JS chunk from 361KB to 832KB raw, because `CodePlayground` was statically imported by `LessonPage`, which is loaded on every lesson view regardless of whether that lesson has a playground. The fix, one level up from M3.7's dynamic-import-of-a-library fix: `React.lazy()` wraps the *entire component*, not just Pyodide inside it —
```typescript
const CodePlayground = lazy(() =>
  import('../components/CodePlayground').then((m) => ({ default: m.CodePlayground }))
)
```
— restoring the main chunk to 360.98KB. This is a layered defense: `React.lazy` defers fetching CodeMirror/the component itself until a lesson actually renders a playground; the Pyodide runtime *inside* that component is separately deferred again until the learner actually clicks Run. Two independent lazy-loading boundaries for two independently expensive resources.

**2. Output buffer scoped incorrectly, discarding valid output.** The original error handler discarded any `stdout` printed before an exception — `print("ok")` followed by a crash showed only the traceback, silently dropping "ok". The fix: declare `buffer` *outside* the `try` block (not inside), so the `catch` handler can still read whatever was accumulated before the exception, and prepend it to the traceback — matching what a real terminal actually shows when a script prints output and then crashes partway through. This was caught **live in-browser during verification** (running a deliberate `1/0` after a `print`), not by static code review — a good example of why "run it and look" matters even for a small, seemingly-obvious code path.

## Why Pyodide (and not server-side sandboxing, or a JS-based Python interpreter)
- **No server attack surface at all**: the server never receives, parses, or executes the learner's code — there is no sandbox to escape because there's no server-side execution happening in the first place.
- **Real CPython semantics**: a genuine Python traceback (`ZeroDivisionError`, correct line numbers, real stdlib behavior) rather than an approximation — important for a *learning* tool specifically, where subtly wrong error messages would actively mislead a beginner.
- **The honest cost**: a multi-MB one-time download and real (if not huge) CPU cost running WASM instead of native code — acceptable for interactive, ungraded practice; this trade-off is revisited more explicitly in M3.10, which reuses this exact execution model for a case (grading) where the stakes of "learner controls the sandbox" are higher.

## Terms worth knowing
- **WebAssembly (WASM)**: a low-level, near-native-speed bytecode format that runs in a browser's JS engine — the compilation target that lets a large existing C codebase (CPython's own interpreter, in Pyodide's case) run client-side.
- **Sandboxing**: isolating untrusted code so it can't affect anything outside its intended boundary — server-side sandboxing (containers, VMs, seccomp) is a genuinely hard problem to get airtight; running client-side in the *learner's own browser* sidesteps the problem for this specific server, since the only thing at risk is the learner's own tab.
- **Module-level singleton (in a frontend context)**: a value created once at module load / first use and reused by every component instance, rather than re-created per component — used here specifically to avoid redundant multi-MB downloads.
