# M1.1 — PostgreSQL Connection + SQLAlchemy Setup

## One-line summary
Gave the backend a working, reusable connection to a real Postgres database — the foundation every model (users, courses, chat, exercises) is built on.

## The problem
An API server needs somewhere to persist data. Opening a fresh database connection per request is slow and doesn't scale; the standard fix is a **connection pool** managed by an ORM.

## What we built
- `backend/app/db/session.py` — the SQLAlchemy engine and a `SessionLocal` factory
- `backend/app/db/base.py` — the declarative base every model inherits from (see M1.3)
- `GET /health/db` — proves the connection actually works end-to-end

## How it works
```python
engine = create_engine(settings.database_url)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

- **`engine`**: manages a pool of actual TCP connections to Postgres. Created once at import time, reused for the life of the process.
- **`SessionLocal`**: a factory for `Session` objects — a session is a single "unit of work": a scope of operations (queries, inserts) that either all commit together or roll back together.
- **`get_db()`**: a **generator function** used as a FastAPI dependency (`db: Session = Depends(get_db)`, seen in every route that touches the database). FastAPI calls it, gets a fresh session via `yield`, hands that session to the route function, and — critically — after the route returns, control comes back to this function *after* the `yield`, running the `finally: db.close()`. This guarantees the connection is returned to the pool even if the route raised an exception, without every route having to remember to close it manually.

`autocommit=False, autoflush=False`: nothing is written to the database until code explicitly calls `db.commit()` (see `auth.py`'s `register()` or `exercises.py`'s `submit_exercise()`) — no implicit writes happening as a side effect of just building query objects.

## Why PostgreSQL (and not SQLite/MySQL)
- **Real concurrent writes.** SQLite locks the whole database file per write — fine for a single-user script, not for a multi-user web app with concurrent requests.
- **Rich column types used elsewhere in this project**: native `UUID` type (every model's primary key, via `UUIDPrimaryKeyMixin` — see M1.3), and a real `ENUM` type (`Message.role` in `models/chat.py`) enforced at the database level, not just in application code.
- **Industry-standard for this kind of app** — the default choice for a serious relational workload, and the one most interview questions about database design assume.

## Why SQLAlchemy (and not raw SQL, or a different ORM)
- **The "2.x style" used throughout this project** (`select(...)`, not the older `Query()` API) is explicit about what SQL will actually run — `db.scalars(select(Course).order_by(Course.title)).all()` reads almost like the SQL it generates, unlike some ORMs that hide the query shape entirely.
- **Alembic (M1.2) is built to work with SQLAlchemy's model metadata** — the two are designed as a pair.
- Raw SQL strings scattered through route handlers would work, but lose type-checking, autocomplete, and — critically — the ability to autogenerate migrations by diffing models against the live schema.

## Terms worth knowing
- **ORM (Object-Relational Mapper)**: a library that lets you work with database rows as Python objects (`Course`, `Lesson`) instead of writing raw SQL strings everywhere.
- **Connection pool**: a set of already-open database connections reused across requests, since opening a new TCP connection to Postgres per request is comparatively expensive.
- **Session / unit of work**: a scope of database operations that commits or rolls back as one atomic group.
- **Dependency injection (FastAPI style)**: a route declares what it needs (`db: Session = Depends(get_db)`) and the framework supplies it, rather than the route constructing its own dependencies inline.

## If asked in an interview
> "I used SQLAlchemy 2.x's `select()`-style query API against Postgres, with a `get_db()` generator as a FastAPI dependency — it yields a session to the route and guarantees the session is closed in a `finally` block afterward, even if the route raises, so no route has to remember connection cleanup itself."
