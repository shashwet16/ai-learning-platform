# M1.3 — Base Model Mixins

## One-line summary
A shared `id` (UUID) and `created_at`/`updated_at` pattern that every model in the project (except one deliberate exception) reuses instead of redefining.

## The problem
Every table needs a primary key, and most need to know when a row was created and last changed. Copy-pasting those column definitions into every model file is repetitive and, worse, easy to make subtly inconsistent (one model using an auto-incrementing integer ID, another using UUID; one missing `updated_at`).

## What we built
`backend/app/models/mixins.py`:
```python
class UUIDPrimaryKeyMixin:
    id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), primary_key=True, default=uuid.uuid4
    )

class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), onupdate=func.now()
    )
```

Every model in the project declares both, e.g. `class Course(UUIDPrimaryKeyMixin, TimestampMixin, Base):` — Python multiple inheritance, but used here purely as a way to compose reusable column sets, not for behavior/polymorphism.

## How it works
- **UUID primary keys, not auto-incrementing integers.** `default=uuid.uuid4` generates the ID in Python *before* the insert happens. This matters: an integer auto-increment ID is only known *after* the database assigns it, and IDs are sequential/guessable (`/courses/1`, `/courses/2`, ...) which leaks information (how many rows exist, in what order they were created) and makes enumeration attacks trivial. A random UUID reveals nothing and can even be generated client-side before a row is ever saved.
- **`server_default=func.now()`**, not a Python-side default — the timestamp is generated *by Postgres* at insert time (`now()` is a Postgres SQL function), not by the application server's clock. This matters if a fleet of app servers isn't perfectly clock-synced, or if a row is ever inserted directly via SQL, bypassing the application entirely — the database is the single source of truth for "when did this actually happen."
- **`onupdate=func.now()`** on `updated_at` only: SQLAlchemy re-runs this expression automatically on every `UPDATE` to that row, without any route needing to remember to set it manually.

## The deliberate exception: `ExerciseSubmission`
`models/exercise.py`'s `ExerciseSubmission` does **not** use `TimestampMixin` — a submission is an immutable log entry (one attempt, recorded once, never edited), so an `updated_at` column would be meaningless. It has its own `submitted_at` field instead (the name the roadmap itself specifies), playing the role `created_at` plays elsewhere. This is a good example of *not* applying a shared pattern just because it's available — the mixin is a convenience, not a rule to follow blindly when the underlying assumption (rows get updated) doesn't hold.

## Why mixins (and not just repeating the fields in every model)
- **Consistency by construction**: it's impossible for a new model to accidentally use an integer ID or forget `updated_at`, because the shared pattern is inherited, not retyped.
- **One place to change the convention**: switching every table's primary key strategy later (hypothetically) is a one-line change in `mixins.py`, not a hunt through every model file.

## Terms worth knowing
- **Mixin**: a class meant to be combined with others via multiple inheritance purely to share a piece of reusable structure/behavior — not meant to be instantiated on its own.
- **UUID (Universally Unique Identifier)**: a 128-bit value, effectively globally unique without any central coordination — unlike an auto-increment integer, which requires the database to hand out the next number in sequence.
- **`server_default` vs. a Python-side default**: `server_default` is evaluated by the database engine itself at insert time; a plain Python default (`default=...` on a non-DB field) would be evaluated by the application, which can differ if there are multiple app servers or direct SQL access.

## If asked in an interview
> "Every model shares a `UUIDPrimaryKeyMixin` and `TimestampMixin` via multiple inheritance, so IDs are random UUIDs generated client-side before insert — not sequential integers, which would leak row counts and enable enumeration — and timestamps come from the database's own clock via `server_default=func.now()`, not the app server's clock. The one deliberate exception is `ExerciseSubmission`, which skips `TimestampMixin` entirely since a submission is an immutable log entry with no `updated_at` to track."
