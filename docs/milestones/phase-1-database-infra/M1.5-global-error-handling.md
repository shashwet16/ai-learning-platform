# M1.5 — Global Error Handling

## One-line summary
Every error the API returns has the same predictable JSON shape — never a raw Python traceback leaking to a client.

## The problem
By default, an unhandled exception in a web framework can leak a stack trace to the client — an information disclosure risk (reveals file paths, library versions, sometimes query fragments) and just a bad API experience (`{"detail": "Internal Server Error"}` with no machine-readable code a frontend can branch on). Different failure types (validation error, not-found, duplicate email, truly-unexpected bug) need a *consistent* response shape so the frontend can handle all of them the same way.

## What we built
`backend/app/core/errors.py`:
- `AppError` — a custom exception class routes raise deliberately, carrying a `status_code` and a machine-readable `code`
- Four registered exception handlers, covering: `AppError` itself, Starlette's base `HTTPException`, Pydantic's `RequestValidationError`, and a catch-all `Exception`

## How it works
```python
class AppError(Exception):
    def __init__(self, message, *, status_code=400, code="bad_request"):
        ...

def _error_response(status_code, code, message):
    return JSONResponse(status_code=status_code,
                         content={"error": {"code": code, "message": message}})
```
Every error path in the app converges on that same `{"error": {"code": ..., "message": ...}}` shape. Route code raises `AppError` when it wants control over the specifics — e.g. `auth.py`'s `raise AppError("Email already registered", status_code=409, code="email_taken")` — and the frontend can check `err.code === 'email_taken'` (see `frontend/src/api/client.ts`'s `ApiError` class) to branch on *why* a request failed, not just parse a human sentence.

One handler is registered against Starlette's *base* `HTTPException`, not FastAPI's subclass, with a comment explaining exactly why:
```python
# Starlette's own router raises the *base* class directly for an unmatched
# route (no handler found), and a handler registered only for
# fastapi.HTTPException would never catch that — exception-handler lookup
# walks the raised instance's own MRO upward, and a subclass is not an
# ancestor of its base class.
```
This is a real, non-obvious Python/FastAPI detail: exception handler dispatch matches by walking *up* the exception's own class hierarchy (MRO — Method Resolution Order), never down into subclasses. Registering against the base class catches both a raw 404 from the router itself *and* any `fastapi.HTTPException` a route might raise (since that subclass has the base class in its MRO) — registering only against the subclass would silently miss the router's own 404s.

The catch-all handler is the safety net:
```python
@app.exception_handler(Exception)
async def handle_unhandled_exception(request, exc):
    logger.exception("Unhandled exception while processing request")
    return _error_response(500, "internal_error", "Internal server error")
```
This is the boundary where a genuinely unexpected bug (not something a route anticipated with `AppError`) gets logged with its full traceback server-side (`logger.exception`, which includes the stack trace) but the *client* only ever sees a generic, safe message — never the traceback itself.

## Why this design (custom exception + global handlers, not per-route try/except)
- **DRY error shape**: without this, every route would need its own try/except to format errors consistently — 20+ routes each getting a chance to format things slightly differently.
- **Security**: the catch-all handler is a hard guarantee that no stack trace, file path, or internal detail ever reaches a client, regardless of what kind of bug caused the 500 — that guarantee lives in one place, not scattered across every route.
- **A stable frontend contract**: `frontend/src/api/client.ts` can parse `body.error.code` / `body.error.message` from *any* failed request, from any endpoint, without knowing which of the four handlers actually produced it.

## Terms worth knowing
- **Exception handler / global error handler**: a function registered with the framework that intercepts a given exception type (or its subclasses) raised anywhere in a request's lifecycle and converts it into an HTTP response — the route code itself never needs a try/except for it.
- **MRO (Method Resolution Order)**: the order Python searches a class's own type and its ancestors when resolving a match (used here for exception-handler dispatch) — always walks toward more general/base classes, never toward subclasses.
- **Information disclosure**: a security category covering any accidental leak of internal implementation detail (stack traces, file paths, library versions) to an untrusted party.

## If asked in an interview
> "Every error response — validation failures, 404s, deliberate application errors, and truly unexpected exceptions — funnels through the same four global handlers into one consistent `{error: {code, message}}` JSON shape. The catch-all handler logs the full traceback server-side but only ever returns a generic message to the client, so an unexpected bug can never leak internal detail. One non-obvious detail I had to get right: the 404-for-unmatched-route case is raised by Starlette's *base* `HTTPException`, not FastAPI's subclass, so the handler has to be registered against the base class or it silently misses that case."
