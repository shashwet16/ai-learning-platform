# M1.2 — Alembic Migrations Setup

## One-line summary
Every schema change since this milestone is a versioned, reviewable file — never a manual `ALTER TABLE` run by hand.

## The problem
A database schema changes over time (new tables, new columns, new constraints). Without a migration tool, keeping a team's databases — or a dev machine vs. production — in sync means manually remembering and re-running every schema change, in order, forever. That doesn't scale and is easy to get wrong.

## What we built
- `backend/alembic.ini` — Alembic's configuration
- `backend/alembic/env.py` — wires Alembic to this project's actual models and settings
- `backend/alembic/versions/` — one file per schema change, each generated by `alembic revision --autogenerate`

## How it works
```python
# alembic/env.py
import app.models  # registers every model on Base.metadata
from app.db.base import Base

config.set_main_option("sqlalchemy.url", settings.database_url)
target_metadata = Base.metadata
```

Two integration points matter here:
1. **`config.set_main_option("sqlalchemy.url", settings.database_url)`** — rather than hardcoding a database URL inside `alembic.ini` (a second place a connection string could drift from `.env`), Alembic is told at runtime to reuse the app's own `Settings` object. One source of truth for the database URL, not two.
2. **`import app.models`** — this import has no explicit use in the file (hence the `# noqa: F401` comment suppressing the linter's "unused import" warning) but is essential: importing the package runs every model file, which registers each model's table on `Base.metadata`. `target_metadata = Base.metadata` is what `alembic revision --autogenerate` diffs against the live database — without this import, Alembic would see an empty metadata object and think every table needs to be dropped.

Each migration file has an `upgrade()` and a `downgrade()` function — e.g. `bcfc78647b90_add_exercises_and_exercise_submissions.py`'s `upgrade()` creates the `exercises` and `exercise_submissions` tables; its `downgrade()` drops them in reverse order, so a bad migration can be rolled back.

Migrations chain together via `down_revision`, forming a linked list: each file names the revision it comes right after, so `alembic upgrade head` can walk from wherever a database currently is to the latest schema, applying only what's missing.

## A real bug this caught: M4.4's enum downgrade
The roadmap's own progress notes flag that M4.4's migration (adding `Conversation`/`Message`, including `Message.role` as a Postgres `ENUM`) needed a manual fix in its `downgrade()`. This is a known Alembic/Postgres gotcha worth knowing: Postgres `ENUM` types are actual named database objects, not just a column constraint — dropping the *column* doesn't drop the *type*. If `downgrade()` only does `op.drop_column(...)`, running downgrade-then-upgrade again fails because the enum type from the previous run still exists. The fix is an explicit `op.execute("DROP TYPE message_role")` (or SQLAlchemy's equivalent) in `downgrade()`, in addition to dropping the column.

## Why Alembic (and not "just run schema changes by hand")
- **Reviewable, versioned history**: a schema change is a diffable file in a pull request, not an undocumented manual step someone has to remember to run.
- **Autogenerate**: `alembic revision --autogenerate -m "..."` diffs the SQLAlchemy models against the current database and writes most of the migration for you — the human's job becomes reviewing and fixing edge cases (like the enum downgrade above), not writing boilerplate `CREATE TABLE` statements from scratch.
- **Reproducible environments**: any fresh database — a new developer's laptop, a CI runner, staging — reaches the exact same schema by running `alembic upgrade head`, in order, from empty.

## Terms worth knowing
- **Migration**: a versioned, ordered script describing one schema change, with both a forward (`upgrade`) and backward (`downgrade`) direction.
- **Autogenerate**: Alembic's ability to compare live database state against SQLAlchemy model definitions and generate a draft migration automatically — not perfect (enum type changes, table renames often need manual correction) but removes most boilerplate.
- **`head`**: Alembic's term for "the most recent migration" — `alembic upgrade head` always brings a database fully up to date.

## If asked in an interview
> "Schema changes go through Alembic migrations generated from the SQLAlchemy models, never manual `ALTER TABLE`s. One real gotcha I hit: Postgres `ENUM` types are separate named objects from the column that uses them, so a migration's `downgrade()` needs to explicitly drop the enum type too, not just the column — autogenerate doesn't always get that right."
